# 基础知识
## TCP与UDP

### TCP与UDP的区别

1.  连接方式
	1. TCP：面向连接。  传输数据前需通过**三次握手**建立连接，结束后通过**四次挥手**断开连接。
	2. UDP：无连接。  直接发送数据，无需预先建立或断开连接。
2. 可靠性
	1. TCP：可靠传输 。通过确认应答（ACK）、超时重传、数据校验等机制确保数据不丢失、不重复、按序到达。
	2. UDP：不可靠传输。  无确认、重传机制，数据可能丢失或乱序。
3. 传输效率
	1. TCP：效率较低。   因连接管理、可靠性机制等额外开销，传输延迟较高。
	2. UDP：效率高。   无复杂控制机制，传输速度快，实时性更好。
4.  数据顺序
	1. TCP：保证数据顺序。  接收方按发送顺序处理数据包。
	2. UDP：不保证顺序。  数据包可能乱序到达，需应用层自行处理。
5. 流量控制与拥塞控制
	1. TCP：  
		1. 流量控制：通过滑动窗口机制，防止发送方过载接收方。  
		2. 拥塞控制：通过慢启动、拥塞避免等算法动态调整发送速率。
	 2. UDP：无流量和拥塞控制，可能加剧网络拥塞。
6. 开销
	1.  TCP：头部较大（**20~60字节**），包含序列号、确认号、窗口大小等控制信息。 **
	2.  UDP：头部固定仅**8字节**，更轻量。
7. 边界
	1.  TCP：流式传输。  无明确数据边界，接收方可能合并多次发送的数据（如发送两次100字节数据，可能一次接收200字节）。
	2.  UDP：数据报传输。  保留发送时的数据边界（发送两次100字节数据，接收方分两次读取）。
8. 模式
	1. TCP：仅支持**一对一**通信。  
	2. UDP：支持**一对一、一对多、多对多**（广播、多播）。
### 应用场景
- **TCP**：  
  适用于对可靠性要求高的场景，如：  
  - 网页浏览（HTTP/HTTPS）  
  - 文件传输（FTP）  
  - 电子邮件（SMTP/POP3）  
  - 数据库连接  

- **UDP**：  
  适用于实时性优先的场景，如：  
  - 实时视频/语音通话（Zoom、VoIP）  
  - 在线游戏（低延迟需求）  
  - DNS查询  
  - 物联网传感器数据传输  

---

### **总结对比表**
| 特性                | TCP                                  | UDP                                  |
|---------------------|--------------------------------------|--------------------------------------|
| **连接方式**        | 面向连接（三次握手）                | 无连接                               |
| **可靠性**          | 可靠传输（确认、重传机制）          | 不可靠传输                           |
| **传输效率**        | 较低（控制机制复杂）                | 较高（轻量级）                       |
| **数据顺序**        | 保证顺序                            | 不保证顺序                           |
| **流量/拥塞控制**   | 支持                                | 不支持                               |
| **头部大小**        | 20~60字节                           | 8字节                                |
| **数据边界**        | 流式（无边界）                      | 数据报（保留边界）                   |
| **适用场景**        | 可靠性优先（文件传输、网页）        | 实时性优先（视频、游戏、广播）       |

---

### **如何选择？**
- **需要可靠传输**（如文件下载）：选TCP。  
- **需要低延迟或实时性**（如直播、游戏）：选UDP。  
- 某些应用（如QUIC/HTTP3）会在UDP上实现可靠性机制，结合两者优势。
## HTTP与HTTPS

### HTTPS的握手过程

HTTPS 的握手过程本质上是 **SSL/TLS 协议的握手过程**，用于在客户端（如浏览器）和服务器之间建立安全的加密通信通道。以下是 **TLS 1.2** 版本的典型握手流程（以 RSA 密钥交换为例）：

### TCP 三次握手
HTTPS 基于 TCP 协议，因此首先需完成 **TCP 三次握手**，建立 TCP 连接（非 TLS 握手内容，但必不可少）。
### TLS 握手核心步骤
#### **Step 1: Client Hello**
客户端向服务器发送 **Client Hello** 消息，包含：
- 支持的 **TLS 版本**（如 TLS 1.2、1.3）。
- 支持的 **加密套件**（Cipher Suites），如 `TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256`。
- 客户端生成的 **随机数**（Client Random）。
#### **Step 2: Server Hello**
服务器响应 **Server Hello** 消息，包含：
- 选择的 **TLS 版本**和**加密套件**。
- 服务器生成的 **随机数**（Server Random）。
- 服务器的 **数字证书**（包含公钥、域名、CA 签名等）。
#### **Step 3: 证书验证**
客户端验证服务器的证书：
1. 检查证书是否由受信任的 **CA（证书颁发机构）** 签发。
2. 检查证书是否在有效期内。
3. 检查证书中的域名是否与访问的域名匹配。
4. 验证证书链（根证书→中间证书→服务器证书）的完整性。
#### **Step 4: 密钥交换**
- **RSA 密钥交换**（传统方式）：
  客户端生成 **预主密钥（Pre-Master Secret）**，用服务器的公钥加密后发送给服务器。
- **ECDHE 密钥交换**（前向保密）：
  服务器发送 **Server Key Exchange** 消息，包含椭圆曲线参数和签名，客户端和服务器各自生成预主密钥。
#### **Step 5: 生成会话密钥**
客户端和服务器利用以下三个随机数生成 **会话密钥（Session Key）**：
1. Client Random
2. Server Random
3. Pre-Master Secret  
会话密钥用于后续通信的对称加密（如 AES）。
#### **Step 6: 完成握手**
1. 客户端发送 **Change Cipher Spec** 消息，告知服务器后续通信使用会话密钥加密。
2. 客户端发送 **Finished** 消息，包含握手过程的哈希值（供服务器验证完整性）。
3. 服务器同样发送 **Change Cipher Spec** 和 **Finished** 消息。
### **加密通信**
握手完成后，客户端与服务器使用 **对称加密算法**（如 AES）加密数据，并通过 **MAC（消息认证码）** 或 **AEAD（如 GCM）** 保证数据完整性。

---

### **TLS 1.3 的优化**
TLS 1.3 大幅简化握手过程：
1. 合并 **Client Hello** 和 **密钥交换参数**。
2. 服务器在 **Server Hello** 中直接发送证书和密钥交换参数。
3. 握手仅需 **1-RTT（一次往返）**，甚至支持 **0-RTT**（快速恢复会话）。

---

### **流程图**
```
客户端                            服务器
  |----- Client Hello ------------>|
  |<---- Server Hello + Certificate + Server Key Exchange --|
  |----- Pre-Master Secret (加密) -->|
  |<---- Change Cipher Spec + Finished ----|
  |----- Change Cipher Spec + Finished --->|
  |<==== 加密通信开始 ===================>|
```

---

### **关键点总结**
1. **身份验证**：通过数字证书验证服务器身份。
2. **密钥交换**：安全协商对称加密的会话密钥。
3. **前向保密**：ECDHE 等算法确保即使长期私钥泄露，历史通信仍安全。
4. **性能优化**：TLS 1.3 减少握手延迟，提升速度。

---

### **常见问题**
- **为什么需要证书？**  
  防止中间人攻击，确保客户端连接的是真实的服务器。
- **RSA 与 ECDHE 的区别？**  
  ECDHE 支持前向保密，RSA 不支持。
- **TLS 握手会影响性能吗？**  
  是的，尤其是 RSA 密钥交换，但 TLS 1.3 和会话恢复（Session Resumption）可缓解这一问题。

## 一次网络请求的发起过程



从输入网址到获得页面的过程涉及多个网络协议和技术步骤，以下是详细的流程说明：

---

### **1. 输入网址与 URL 解析**
- **用户行为**：在浏览器地址栏输入 `www.example.com`。
- **URL 结构解析**：
  - **协议**（如 `HTTP/HTTPS`）：若未指定，浏览器默认补全（如 `HTTPS`）。
  - **域名**（如 `www.example.com`）：需转换为 IP 地址。
  - **路径与参数**（如 `/index.html?query=1`）：标识服务器上的资源。

---

### **2. DNS 解析：域名 → IP 地址**
- **过程**：
  1. **浏览器缓存**：检查是否缓存过该域名的 IP。
  2. **系统缓存**：查询操作系统 Hosts 文件。
  3. **路由器缓存**：检查本地路由器的 DNS 记录。
  4. **本地 DNS 服务器**：向 ISP（互联网服务提供商）的 DNS 服务器发起查询。
  5. **递归查询**：若本地 DNS 无记录，依次向根域名服务器、顶级域名服务器（如 `.com`）、权威域名服务器（如 `example.com`）查询，最终获取 IP。
- **示例**：
  - 查询 `www.example.com` 时，权威服务器可能返回 CDN 节点的 IP 以加速访问。

---

### **3. 建立 TCP 连接：三次握手**
- **目的**：确保客户端与服务器双方具备收发数据的能力。
- **步骤**：
  1. **SYN**：客户端发送 `SYN` 包（序列号 `x`）。
  2. **SYN-ACK**：服务器返回 `SYN-ACK` 包（序列号 `y`，确认号 `x+1`）。
  3. **ACK**：客户端发送 `ACK` 包（确认号 `y+1`），连接建立。
- **优化**：若为 HTTPS，需在此后进行 TLS 握手。

---

### **4. TLS 握手（仅 HTTPS）**
- **目的**：协商加密算法，验证服务器身份，确保通信安全。
- **步骤**：
  1. **Client Hello**：客户端发送支持的 TLS 版本、加密套件列表、随机数。
  2. **Server Hello**：服务器选择加密套件，返回数字证书和随机数。
  3. **证书验证**：客户端验证证书合法性（如颁发机构、有效期）。
  4. **密钥交换**：客户端生成预主密钥，用服务器公钥加密后发送。
  5. **生成会话密钥**：双方通过随机数和预主密钥生成对称加密密钥。
  6. **完成握手**：双方交换加密后的完成消息，开始加密通信。

---

### **5. 发送 HTTP 请求**
- **请求报文结构**：
```
  GET /index.html HTTP/1.1
  Host: www.example.com
  User-Agent: Chrome/91.0
  Accept: text/html
```
- **关键字段**：
  - **请求方法**：`GET`（获取资源）、`POST`（提交数据）等。
  - **请求头**：`Host`（目标域名）、`Cookie`（会话信息）、`Accept-Encoding`（支持的压缩格式）。
  - **请求体**：`POST` 请求时携带的表单数据或 JSON。
----

### **6. 服务器处理请求**
- **流程**：
  1. **Web 服务器**（如 Nginx/Apache）：接收请求，根据 URL 路由到后端应用（如 PHP、Node.js）。
  2. **应用服务器**：执行业务逻辑（如查询数据库、调用 API）。
  3. **生成响应**：将结果封装为 HTML、JSON 等格式。
- **静态资源**：直接返回文件（如 HTML、CSS、图片）。
- **动态资源**：通过后端程序生成内容。

---

### **7. 服务器返回 HTTP 响应**
- **响应报文结构**：
  
  HTTP/1.1 200 OK
  Content-Type: text/html
  Content-Length: 1234
  
  <!DOCTYPE html>
  <html>...</html>
  
- **关键字段**：
  - **状态码**：`200`（成功）、`404`（未找到）、`500`（服务器错误）。
  - **响应头**：`Content-Type`（数据类型）、`Cache-Control`（缓存策略）、`Set-Cookie`（设置会话 Cookie）。
  - **响应体**：HTML 内容或 JSON 数据。

---

### **8. 浏览器解析与渲染**
1. **解析 HTML**：构建 DOM（文档对象模型）树。
2. **加载 CSS/JS**：
   - **CSS 解析**：生成 CSSOM（CSS 对象模型）树。
   - **JavaScript 执行**：可能阻塞渲染（需使用 `async/defer` 优化）。
3. **构建渲染树**：合并 DOM 和 CSSOM，确定节点布局。
4. **布局（Layout）**：计算每个节点的位置和大小。
5. **绘制（Paint）**：将渲染树转换为屏幕上的像素。
6. **重绘与回流**：动态修改 DOM/CSS 时触发重新渲染。

---

### **9. 关闭连接或保持复用**
- **HTTP/1.1 默认行为**：保持连接（`Connection: keep-alive`），复用 TCP 通道处理后续请求。
- **关闭连接**：通过四次挥手终止 TCP 连接（若未复用）。

---

### **关键优化技术**
- **CDN（内容分发网络）**：缓存静态资源到全球节点，减少延迟。
- **HTTP/2 多路复用**：单连接并行传输多个请求，避免队头阻塞。
- **浏览器缓存**：通过 `Cache-Control` 和 `ETag` 减少重复请求。
- **资源压缩**：使用 Gzip/Brotli 压缩 HTML/CSS/JS。

---

### **完整流程示意图**
```
用户输入 URL → DNS 解析 → TCP 握手 → TLS 握手（HTTPS） → 发送 HTTP 请求 → 
服务器处理 → 返回响应 → 浏览器解析渲染 → 关闭连接
```

---

通过理解这一流程，开发者能更好地优化 Web 性能（如减少 DNS 查询、启用 HTTP/2），并定位网络问题（如 TLS 证书错误、TCP 连接超时）。

# 拦截器

1. 请求的执行流程：构建请求 -> 分发器 -> 拦截器 -> 获得响应；
2. 分发器：内部维护队列与线程池，用来控制请求数与请求线程；
3. 拦截器：完成请求；
4. 1. RetryAndFollowUpInterceptor：重试与重定向
5. 2. BridgeInterceptor：桥接拦截器
6. 3. CacheInterceptor：缓存拦截器
7. 4. ConnectInterceptor：连接拦截器
8. 5. CallServerInterceptor：请求服务器拦截器

## RetryAndFollowUpInterceptor

1. 重试用来处理特定的IO异常和路由异常
2. 1. 重试是可配置
3. 2. 部分异常如协议异常，握手异常 证书异常 不能重试
4. 3. 存在更多路径选择，DNS解析返回了多个IP ，挨个重试` RouteSelector#resetNextInetSocketAddress`
5. 重定向 针对特定的返回码重新请求
6. 1. 407 客户端使用了代理，需要添加Proxy-Authorization请求头，并配置密码；
7. 2. 308：永久重定向，并且请求为Get形式
