# 1. binder
## 基础
1. binder 和其他的进程间通信方式相比，有 3 个优势；
	 1.  利用mmap 实现的一次拷贝；
		1. 服务端的进程启动后就会立即打开 binder 驱动，调用 `binder_mmap`，预留用户空间的一段虚拟地址作为接收数据的缓冲区，整个区间记录为一个空闲 binder_buffer；
		2. 客户端发起事务时，通过 `BINDER_WRITE_READ` ioctl 把 `BC_TRANSACTION` 命令 和`binder_transaction_data` 交给内核。内核先用 `copy_from_user` 把数据的**头部结构体**拷入内核空间、解析具体命令，然后根据传来的binder句柄（handle），经由 `binder_ref` 找到对应的 `binder_node`，定位到目标进程；
		3. 内核在目标进程中分配 binder_buffer ，安装物理页，内核映射到同一页，再一次调用 `copy_from_user`，把客户端的真正的数据逐页拷贝到物理页中；
			1. copy_from_user 必须要经过内核空间，写入物理内存也必须要通过虚拟地址；
		4. 拷贝完成后，唤醒服务端线程，在`binder_thread_read` 中，把通过 binder_buffer 记录的数据在服务端进程内的虚拟地址连同`BR_TRANSACTION` 命令填入 `binder_transaction_data`中，内核调用 copy_to_user 把头部结构体拷贝到服务端，服务端通过地址直接访问这块内存，零拷贝读取；
	2. 由内核保证的权限校验可靠性
		1. 内核在binder_transaction方法中处理事务时，会将客户端的的 uid 和 pid 写入binder_transaction_data中;
		2. 服务端读取并保存在当前工作线程中，通过 pid 和 uid来进行权限校验；
		3. 并且提供了 clear 和 restore 方法来切换 PID 和 UID，适用于需要自己的身份来执行的操作。
	3. 基于 C/S 的架构设计
		1. Binder采用C/S架构和分层设计，客户端通过代理形式直接使用服务端接口方法，在应用层，framework层，native层，内核层，客户端和服务端分别持有不同的binder对象；
			1. 应用层，客户端持有服务代理，服务端实现具体服务逻辑;
			2. 在framework层，客户端对应BinderProxy对象，服务端对应Binder对象;
			3. 在navite层客户端对应BpBinder，服务端对应BBinder;
			4. 在内核层，客户端对应binder_ref，服务端对应binder_node;
		2. Binder 对象在传递时，服务端进程把它的 `BBinder` 序列化为 `flat_binder_object` 写入 Parcel，内核读取后，分别在客户端进程和服务端进程创建 binder_ref  和 binder_node，binder_ref指向binder_node，调用时通过handle定位找到对应 ref 和node 。
		3. 对于实名服务，如AMS，WMS 通过句柄0进入service_manager 指名查询，对于匿名服务，用传递binder对象时生成的动态句柄handle进行访问 。
## oneway
1. oneway方法属于异步调用，客户端立即返回，不阻塞，方法也不允许有返回值；
2. 内核在下发BR_TRANSACTION 事务时，对于 oneway ，将调用 pid 置为 0， 服务端无法获得调用者的 PID；
3. 同一个 Binder 对象的 oneway 事务串行执行，并且内核中限制 oneway 使用的buffer 大小为总空间的一半
## AIDL
1. 支持的数据类型：基本数据类型/String/CharSequence/`List` 和`Map` （ 其中的元素必须是 AIDL 支持的类型)/ 其他 AIDL 接口/实现了 `Parcelable` 接口的自定义对象
2. 生成的 Java 文件中包含
	1. 接口本身
	2. 描述符：全限定名，Binder 的身份标识；
	3. 事务码 `TRANSACTION_*`：方法的编号；
	4. 服务端 `Stub`类 继承 Binder和接口
		1. 方法 asInterface ，判断客户端和服务端是否属于同一进程，属于则返回 Stub，否则返回 Proxy;
		2. 方法 onTransact，根据事务码路由到接口的实现；
	5. 客户端 Proxy：持有Binder 代理，在跨进程调用中作为服务端在客户端的代理；
3. `in`, `out`, `inout` 关键字：用于修饰方法的参数，表示数据的流向，只对Parcelable 类参数**和对应的集合有意义；
	- `in`（默认）：调用方→被调方单向传入；被调方修改**不会**传回。
    - `out`：用于回传；调用方原始值不发送，被调方赋值后传回；
    - `inout`：双向流动。
## linkToDeath
1. 客户端通过 linkToDeath，将死亡回调加入的 BpBinder 的列表中，同时向内核发送BC_REQUEST_DEATH_NOTIFICATION命令，分配 binder_ref_death， 挂到对应 binder_ref 上，binder_ref_death 会记录对应的 BpBinder;
2. 在内核中，当binder_node 对应的进程死亡，会通过 binder_refs 找到所用引用了它的客户端，唤醒客户端的 binder 线程，写入BR_DEAD_BINDER命令，根据binder_ref_death记录的 BpBinder 找到对应列表逐个通知；

# 2.  协程
## 实现原理
1. kotlin 中的 协程是一种轻量级的线程操作框架；
2. 协程的实现有2个核心的概念
	1. 第一个概念是挂起与恢复：
		1. 挂起函数采用 suspend 修饰，经过编译之后会注入一个续体类型的参数，同时会在方法体内创建一个匿名续体接受这个参数;
		2. 续体接口Continuation会持有协程上文和唯一方法resumeWith ，匿名续体会继承ContinuationImpl 实现其 invokeSuspend 方法；
		3. 这个匿名续体在挂起函数中的作用称为“CPS 状态机”
		4. 它通过 int 值label 记录每个子挂起函数的状态，执行到子函数前，状态+1，子挂起函数立即返回常量COROUTINE_SUSPENDED，挂起协程，释放线程，并将当前续体交给子函数；
		5. 当子函数异步操作完成之后，调用续体的 `resume` 接收函数的执行结果，执行其invokeSuspend，再次进入状态机，执行下一个状态，直到函数返回；
	2. 第二个概念就是结构并发,通过层级化的作用域和父子关系来管理协程的生命周期，确保所有并发任务都能被正确完成、取消和异常处理。核心实现由 Job 对象完成，Job 是协程上下文的一种。启动协程会返回一个Job，表示一个协程任务。
		1. Job 的生命周期包含：
			1. New：协程已创建但未启动（例如通过 `launch(start = CoroutineStart.LAZY)`）。
			2. Active：协程正在运行（默认状态）。
			3. Completing：协程已执行完毕，等待子协程完成。
			4.  Completed：协程及其所有子协程均已完成。
			5. Cancelling：协程正在取消，调用 cancle方法，等待子协程取消；
			6. Cancelled：协程已取消。
		2. Job提供操作父子Job的接口来管理父子协程。父 Job 取消时，所有子 Job 自动取消，子 Job 的异常默认会传播到父 Job。
			1. 常见的SupervisorJob的childCancelled方法返回 false，表示不处理子协程的取消消息。
## 线程调度 CoroutineDispatcher
1. CoroutineDispatcher是协程的分发器，它是协程上下文的一种，本质是通过线程池或者特定的线程 Handler来完成线程的切换；
2. 续体通过 intercepted方法来结合协程上下文中Dispatcher，组合DispatchedContinuation，将续体的 resume 方法调度到指定线程上来完成的线程切换。
3. 系统提供的分发器有 4 种：
	1. Default：线程数与 CPU 核心数相关，为 CPU 密集型任务设计；
	2. IO：可动态扩展线程数，默认为64个，为IO 密集型任务设计；
	3. Main：指定 主线程（UI 线程） 执行任务
	4. Unconfined：不限制协程的线程，启动时在调用者线程执行，恢复时跟随触发恢复的线程；

## 协程与线程的对比
1. 线程由内核完成调度，切换成本大；创建内存开销大，有数量限制，生命周期管理困难；
2. 协程是一种构建在用户空间轻量级的线程操作框架，只是运行在线程上的任务，~~核心概念是挂起与恢复和结构化并发~~，一个线程可以运行多个协程，没有数量限制；
# 3. 卡顿优化

## 思路
1. 卡顿问题通过perfetto_trace 来进行分析，一帧数据的绘制流程，涉及应用的 UI 线程 /渲染线程 和 SurfaceFlinger ，应用端重点关注 的是UI 线程，常见的问题点有：
	1. 业务异常 、跑小核导致的UI 线程 Running 超时；
	2. Binder调用、GC 、线程优先级设置错误 、CPU负载高导致的Runnable超时；
## 实际处理的问题：广告抽屉的滑动超时
本地抓取展示广告数据时抽屉滑动 trace结合用户反馈的卡顿 trace，定位到导致UI 线程耗时滑动卡顿的原因有3 个
	1. measure 次数异常：广告类型的 Item 无高度缓存，抽屉的 RecyclerView 列表在滑动的过程中，需要根据position 位置 ，动态计算滑动距离与滚动条联动，对于没有缓存的item 类型则需要主要 measure获取高度；解决方案：固定 Item 高度并缓存；
	2. binder 调用阻塞：在 onBinderViewHolder 中，调动 PKMS的接口，检查item 绑定的应用数据的安装状态，根据是否安装来展示对应 UI；
		1. 解决方案：缓存数据的状态，统一数据的更新入口，取消bindViewHolder 中的数据的 check 操作;
	3. UI 线程 阻塞等待 GC：将抽屉滑动过程加入的 GC 抑制列表中；
		1. GC 抑制针对的是 BackGroundGC;
		2. 采用 inline hook，将ConcurrentGCTask 的 Run() 方法作为 hook 点，执行对应业务时，在 hook 函数中，休眠 线程一段时间，结束后，再重新调用 ConcurrentGCTask 的 Run 方法；
	4. 其他的优化手段包括
		1. 重写了 DiffUtils的 Callback，增加包名和图片地址的判断；

## 泄露
### Leakcanary的实现原理
1. Leakcanary是内存泄露检测框架，默认实现了对Activity/Fragment/Service/View 这四种对象的监控；
2. 框架分为 2 个部分，泄露对象的检测和分析最短泄露引用链；
3. 检测泄露对象分为2步：
	1. 监控对象销毁：
		1. Activity/Fragment：系统提供接口监听；
		2. Service：系统没有提供统一的生命周期监听方法，需要通过hook ActivityThread中的主线程Handler的STOP_SERVICE消息和AMS中的`serviceDoneExecuting`方法 ，确认要销毁的服务。
		3. View：这个View指DecorView，应用中的所有的DecorView都是保存在全局WindowManagerGlobal集合中，通过监听集合的添加和删除来实现对View的生命周期的监控。自定义集合实现对添加删除的监听反射替换WindowManagerGlobal中的集合；
	2. 当对象被销毁时，创建关联的弱引用并加入到全局引用队列中，5s后检查这个队列，如果这个对象被成功回收，队列就出会出现该对象，否则泄露；
4. 引用链分析：内存泄露发生后，dump当前的hprof文件，通过解析该文件获取最短引用链
	1. `hprof` 文件数据内容由 record 数组构成，每个 record 可以代表一个对象，并且有对应的 tag，收集 tag 为`gcroot`类型的 record。
	2. 遍历 `gcroot`队列，生成一颗以objectid为索引的字典树。根节点objecid 为 0，叶子节点为泄露对象，子节点为gcroot对象中的属性或元素，gcroot的子结点共有三种类型；
		1. 对于实例对象，子节点就是当前实例和父类中的所有非静态属性对应的对象；
		2. Class 对象，子节点为静态属性；
		3. 对象数组或集合，子节点就是集合非空元素对应的对象；
	3.  从 根节点出发，通过 BFS 逐层查找，第一次找到对象时，路径即为最短路径，生成通知信息；
# 5. ANR
1. ANR 的类型有 4 种
	1. 输入事件超时：应用 5s 内没有完成事件的处理 和key事件5s 内没有找到焦点窗口
	2. 广播超时（前台10s，后台60s）：没有完成onReceive 流程；
	3. 服务超时（前台20s，后台200s），没有完成生命周期方法；
	4. ContentProvider 类型超时，在 10s 内没有完成发布流程；
2. ANR 发生时，完整的日志3种包含：ANR trace  mainlog 日志 和event 日志；
	1. 每个日志都会输出 ANR 时间 、所属进程和原因，首先就是要对比 3 份日志，确认日志有效性；
3. 针对超时类型的 ANR
	1. trace日志中会输出进程内所有线程的状态，主要关注主线程，正常状态下的堆栈会处于Lopper 中等待消息，常见的异常有
		1. 锁阻塞：打印 waiting to lock 锁对象的 `Hashcode `和 持锁线程 id，定位到具体线程堆栈分析；
		2. 主线程执行耗时操作：打印耗时方法堆栈；
	2. 主线程正常时，关注 mainlog 中输出的 CPU负载信息和内存信息
		1. CPU 负载信息中包含各个进程的CPU占用率，每个核的满载为 1，是多个核心的累加结果，检查占用率和 iowait 是否正常。
		2. 内存信息 主要观察进程的onTrimMemory 打印， 值越大内存越紧张以及；`oom_adj` **数值越小，进程优先级越高，越不容易被系统杀死；数值越大，优先级越低**
		3. 其他的重要日志还可以关注`low_memory`、`lowmemorykiller` `am_kill`等 tag；
4. 针对无焦点窗口的 ANR，主要关注的是 event 日志中的 input_focus tag；
	1. 无焦点窗口的 ANR 问题是针对 key事件, 所以最常见的场景就是 monkey，key 事件派发时，Inputdispatcher需要从记录的数据中查找焦点窗口;
	2. 焦点窗口信息的流转涉及 WMS -> SurfaceFlinger  -> InputDispatcher
	3. 对于 WMS：从 main 日志中过滤 Changing Focus，对比正常路径找到异常点；
		1. 最常见的有2 个路径第一个就是就是relayoutWindow：窗口添加成功之后在WMS 处理窗口属性 和 应用热启动时调用focusedTask 请求更新焦点时；
	4. 对于 SurfaceFlinger
		1. 当 焦点窗口发生变化，窗口信息作为事务的一部分，与窗口属性一起提交给 SurfaceFlinger。结合present中打印 Layer来判断参与合成的窗口信息。
	5. InputDispatcher 结合event 日志中的 `input_focus` tag 分析，产生的日志有 4 种
		1. Requesting ：请求将focus置为null；:由WMS输出，A1 pause执行完， 失去焦点，A2 Starting Window 添加成功，
		2. Focus leaving ：焦点离开对应窗口；焦点离开A1，由InputDispatcher 输出
		3. Focus Request ：请求将焦点更新为对应窗口：由WMS输出，窗口relayout完成，请求焦点；
		4. Focus entering： InputDispatcher完成焦点的更新；
	6. 具体问题
		1. 在 应用 Activity A1 底部滑动导航栏切换应用，同时启动 A2，A2启动完成之后立即 fininsh;
		2. 产生了 3 个 Transition , recentTransition，openTransition， closeTransition
		3.  其中由于同步机制，closeTransition 最后结束(参与closeTransition的窗口同时参与了recentTransition，openTransition，进入了同步状态)，
		4. 正常 close Transition 在启动时会分别收集 Activity A1和A2 的窗口信息，并将 A1的过渡模式设置为前台 ，并让A1的窗口在 Shell 侧跟随过渡动画结束事务提交显示；
		5. 但是在此异常场景的Transition收集过程时，recent窗口是焦点窗口，判断 A1和A2都要隐藏，将Transition 的收集窗口提升到 Task 级别，并在结束时隐藏了整个 Task , 导致此时 没有焦点窗口；
		6. 解决方案：就是在 CloseTransition 最后结束回调中，判断焦点栈的栈顶 Activity 是否与需要隐藏的一致，一致则发生了异常，不隐藏，并强制触发焦点更新和图层的重绘；~~

# 6. Launcher 
## 图标加载流程
1. Launcher Activity在启动时，由 `LauncherModel` 触发 `LoaderTask` 在后台线程运行，加载数据，加载数据分为 3 个阶段；
	1. 首先从 launcher.db 中读取Workspace的图标数据后，切换到主线程将数据绑定到 Workspace；
	2. 之后加载所有的应用数据，切换到主线程将数据绑定到抽屉；
	3. 最后在加载并缓存插件和快捷方式数据；
2. Launcher首次启动时， 从 `default_workspace.xml` 等资源中解析默认布局写入launcher.db;
3. 加载优化：
	1. 分屏加载，加载 Workspace 数据时分屏加载，每一屏的的应用信息和图标加载完成之后切换到主线程 UI绑定，不等待所有数据加载完成；
	2. 消除 `waitForIdle()` 轮询，原生在加载过程的每个阶段中，通过 IdleHandler机制，让 LoderTask 所属`MODEL_EXECUTOR` 后台线程等待主线程处理完所有的工作进入空闲之后才开始继续加载，完全放弃了并发，每次阻塞最长等待 1s，首屏绑定完成时，移除等待，让`MODEL_EXECUTOR`线程与主线程并行运行；

## 桌面拖拽流程
以`1*1`的图标为例，介绍图标的拖拽流程。
1. 长按BubbleTextView 弹出快捷方式列表，触发预拖拽，创建并显示DragView，隐藏BubbleTextView，对应用图标来说就是只包含图片不包含标题的ImageView;
2. 同时创建对应的DragDriver，桌面处理触摸事件是通过DragLayer下发给对应TouchController进行处理，只有DragDriver不为空时，才下发到DragController，后续的触摸逻辑由DragController接管；
3. 当手指移动超过阈值时，结束预拖拽，隐藏弹窗，同时桌面进入到Spring_Loaded状态，执行对应的状态动画；
4. 手指移动过程中，遍历 CellLayout， 根据每个网格到DragView的距离，找到最近网格
	1. 如果网格中已经存在图标则根据停留时间与距离触发组成文件夹和挤位逻辑，不存在图标，直接绘制落点预览背景；
5. 拖拽中最复杂的挤位方案的选择
	1. 首先根据DragView与目标网格的位置计算出挤位方向，这是一个大小为2的向量数组，由它们与坐标轴的角度计算得到，值可以为 -1,0,1。组合成上下左右和4个对角线8个方向；
	2. 挤位方案有 3 种：
		1. 原地放置：距离最近的目标网格如果被占用则失败，优先级最低；
		2. 空位放置：遍历 CellLayout 找到第一个空位网格放置，优先级其次；
		3. 挤位放置：
			1. 沿着挤位方向，整体推移图标，推挤过程会传递，如果推A的过程遇到B，B也会被一起推；
			2. 左右挤位调整 x，上下挤位调整 y。对于对角线方向，进行坐标拆分会先尝试左右,之后在上下，超过边界会挤位失败，失败后反转向量数组，尝试向反方向进行推移，对角线方向就会尝试4次；
			3. 挤位失败则尝试将目标区域图标保持相对位置不变整体移动到最近的空位上。
			4. 移动失败则单独为每个目标区域的图标找空位网格；
	3. 得到全新的坐标后，播放位移动画；
6. 松手后，移除原位置BubbleTextView，并加入到目标网格对应的CellLayout中，修改数据库中布局数据，播放位移动画将DragView移动到目标网格，动画结束后，显示出BubbleTextView；

# 7. Shell Transition 之启动应用的动画流程
1. WMCore：运行在system_server进程的模块，其核心类包含
	1. TransitionController：主要负责管理整个过渡动画的生命周期，比如WindowContainer 的收集，等待，启动等;
	2. Transition：具体过渡动画的实体类，它的主要生命周期包含收集中（collecting），启动（started） ，播放中（playing），结束（finished)；
	3. SyncGroup： 等待所有参与者Window 绘制完成；
2. WMShell: 运行在SystemUI进程的模块，其核心类包含
	1. Transitions：主要负责过渡动画的具体播放逻辑；
	2. ActiveTransition：具体过渡动画的实体类，每一个轨道都有唯一ActiveTransition，轨道相同merge；
	3. TransitionHandler：动画播放的句柄;
3. 桌面在启动应用时，构造的ActivityOptions将RemoteTransition打包，桌面通过RemoteTransition接收leash(SurfaceControl) 播放窗口动画；
4. 进入到AMS后，ActivityStarter启动Activity前通过TransitionController创建Transition，并将状态置为收集中，并同时初始化SyncGroup用于检测所有参与窗口的状态；
	- 在启动场景中，自动收集 visible 发生变化的窗口，也就是应用的ActivityRecord和Task，Launcher的ActivityRecord和以及壁纸；
5. Activity 启动完成，通知Shell，完成ActiveTransition和TransitionHandler的初始化，之后Transition进入启动状态；
6. 等待应用的 StartingWindow 绘制完成，所有窗口就已经准备就绪 ，回调Transition的onTransactionReady，准备启动事务和结束事务 交给 shell的onTransitionReady，进入播放状态；
7. 启动事务：会新建根节点，将关联窗口reparent到此节点，播放时再根据窗口信息新建 Surface 统一隐藏或显示；
8. 结束事务: 将窗口reparent到正常窗口树；
	1. 在启动过程为例：A ->B，动画播放时A，B都会显示；动画结束B显示，A隐藏；
9. 动画结束，桌面端回调finish callback，在 Shell侧提交结束事务，通知 core 更新 Activity 的可见状态，Transition进入结束状态；

			3. 设置一定的条件，比如 Java堆内存就是占比超过 0.8 同时相比上次减少小于 0.0.5或者超过 0.9或者增幅达到 300m。触发 3 次则 dump hprof 文件内存信息裁剪上报。
	2. dump hprof文件不仅是一个耗时操作而且会挂起进程
		1. koom通过fork 创建子进程，在子进程中进行dump；
		2. 由于 fork 不支持多线程，fork 前还需要调用 suspendAll 方法，挂起所有线程，子进程创建完在恢复执行。

			1. fork 会完整拷贝父进程的状态，包括代码段，数据段，堆、栈等；

	1. 主动捕获 Bitmap 的处理过程中中 OOM，进行二次压缩处理；
	2. 在 onTrimMemory 回调中，内存紧张时，主动清理缓存、释放UI资源等；

# 9. 动态化换肤 
1. 插件化换肤是指通过从服务端下载主题包，在不重启app的前提下，实现颜色，背景，以及自定义属性的替换；
2. 要实现这个需求，在流程上主要分为2步：
	1. hook应用中View的创建过程，保存支持动态替换的View及其对应的属性列表；
	2. 创建插件Resource对象，在保证插件与主 App中的资源名称和类型一致的前提下，通过名称和类型以反射的形式从插件Resource中找到对应属性设置给View； 
3. hook应用中View
	1. View是在LayoutInflater解析xml时，通过xml中指定的全类名反射创建的；
	2. 在反射时，Inflater提供了一个Hook点，允许应用自定义反射过程，比如androidx  中的AppCompatActivity，就会通过这个方法将TextView ，ImageView 替换为AppCompatTextView,AppCompatImageView ；
	3. 参考AppCompatActivity写法，在Activity onCreate前（ActivityLifecycleCallback），将自定义工厂设置给Inflater；
4. 加载插件Resource
	1. 通过Context获取资源时，最终是通过AssetManager方法获取；
	2. AssetManager 允许通过资源的文件路径进行创建;
	3. 这样传入下载的资源包路径就可以创建插件Resource;
5. 在实践中遇到的问题就是，如何修改隐藏API 的问题。
	1. `LayoutInflater` 的 `Factory` 通过一个私有 `boolean` 标志位控制，只允许设置一次。`AppCompatActivity` 已经设置了它，导致无法再次覆盖；
		1. 在 Android 10 之前可以直接反射修改，之后，这个属性被设置为隐藏 api，不允许应用调用；
	2. 我采用的方案是不修改底层代码，完全基于Java 中Unsafe和 MethodHandle实现；
	3. Unsafe 允许通过访问和修改对象的内存地址来控制属性的访问；
	4. MethodHandle是反射API 的一种替代，其artFieldOrMethod字段指向了属性和方法的内存地址，是操作目标类方法和属性的句柄；
	5. 具体的实现流程可以分为 3 步：
		1. 通过 Unsafe 获取Class 的 Class 对象 iFields 属性的偏移地址，根据此地址得到目标类的iFields属性地址， 此地址可以理解为目标类属性集合的首地址；
		2. 接下来就是要获取每个属性的内存大小，在工具类定义 2 个已知属性，通过Unsafe获取它们各自对应的MethodHandle中artFieldOrMethod字段的地址 ，比较两者的差值，计算出每个属性内存大小；
		3. 从前面 2 步中，得到了属性集合首地址和每个属性的大小。就可以通过 Unsafe替换已知属性的artFieldOrMethod地址为目标类属性地址，再通过 MethodHandle 读取和修改这个目标字段；
# 10. 闪屏 黑屏 定屏 问题
## 必现闪屏
1. 半屏的 DialogActivity A1 ，A2; A1 启动到A2 和 A2 退出回到 A1 都出现闪屏；
2. 跟踪winscope，发现是Dim图层显示异常；Dim图层是挂载在Task下的图层，会通过 RelativeLayer 到绑定栈顶的 ActivityRecord ，并设置z-order为-1, 显示在Activity下方；
3.  问题的就是启动和退出过程中，Dim 没有及时更新它的父容器并提交显示；
	1. Dim 图层的更新由Choreographer.FrameCallback回调触发，遍历栈内的 Activity，只检查ActivityRecord的visible属性；
	2. A1 启动 A2 的过程中，A2对应ActivityRecord的visible属性在 core 侧设置完成，A2 窗口的显示需要在 Shell 侧过渡动画开始播放时；
	3. A2 退出回到 A1 的过程中，A2窗口的隐藏 ,跟随过渡动画的结束事务在 Shell 侧提交，但 A2 的 visible 属性动画结束时由 Shell 通知 到core才进行设置；
	
5. 修改思路：就是将Dim的更新事务与应用启动和退出的过渡动画的开始事务和结束事务合并提交，同时拦截其他更新Dim显示的路径；
6. 修改方式：
	1. 启动时：
		1. 当 A2 对应的 ActivityRecord visible 首次被设置为 true 时，也就是过渡动画开始播放前，将Dim图层 reparent 到 A2，跟随启动事务在 Shell 侧提交；
		2. 同时增加判断如果其他路径设置的窗口与当前一致则返回；
	2. 退出时：
		1. 在 A2 pause完成，A1 开始resume 之后，根据对应Activity的状态，将Dim图层reparent 栈内 resume 的 Activity 也就是A1；
		2. 跟随过渡动画的结束事务提交

## 定屏
1. 分析思路:
	1. dump input events 或者操作下状态栏，导航栏是来排除硬件问题；
		1. dump window / dump SF /  dump input
			1. 确定焦点窗口，定屏问题是有焦点窗口，只是焦点不处理事件
	2. 问题通常就是焦点窗口和焦点应用的异常导致

	1. 透明的 window 覆盖到桌面；
	2. 桌面的近期任务窗口“recents_animation_input_consumer”异常，导致正常窗口无法接收事件
	3. 应用的绘制被阻断，导致界面不更新;
3. Launcher 定屏
	1. Launcher 的“recent”结束异常，焦点窗口停留在“recents_animation_input_consumer”
	2. 这个没有固定思路，通常都是需求引入的，早期在屏蔽 taskbar时，尝试通过隐藏 taskbar图层来实现，但是原生是通过 taskbar 的mergeWithNextTransaction 来提交结束事务。

	2. 怀疑是应用绘制或者是合成的地方异常，首先在 performDraw 加了日志，定位到是灭屏状态异常，导致绘制直接返回，但是首帧会判断单独的 Flag 进行绘制；
	3. 此灭屏状态变更是由 系统服务DisplayManagerService通知是 VRI 注册监听；
	4. 在通知时，根据 uid来判断进程的优先级，如果大于IMPORTANCE_CACHED，则立即通知，否则加入缓存，监听优先级变化；
		1. 当优先级变化时，找到 uid 对应的 pid 进行通知，原生逻辑的异常点就是只通知遍历到的第一个 pid，对于多进程应用会发生遗漏；
