# Java
## 1. JVM的内存模型
1. 程序计数器：线程私有，记录当前线程的字节码执行的行号指示器;
2. Java虚拟机栈：线程私有，每个方法调用对应一个栈帧，栈帧中包含
	- 局部变量表：~~存储方法参数和局部变量~~
	- 操作数栈：~~存储计算过程中的临时操作数，是字节码指令的工作区。~~
	- 动态链接：指向运行时常量池中该栈帧所属方法的引用，用于支持多态；
	- 方法的返回地址：~~记录方法正常退出或异常退出的位置~~。
3. 本地方法栈：与虚拟机栈类似，它为本地方法服务；
4. Java堆：线程共享，几乎所有的对象都在堆上分配，是垃圾回收的主要区域；
5. 方法区：线程共享，存储类的元数据，静态变量和运行时常量池以及即时编译后的代码；
6. 运行时常量池：方法区的一部分，当类被加载后，存储编译期生成的字面量和符号引用~~，在类加载的解析阶段，一部分符号引用会被替换为直接引用，~~并支持动态添加常量，如String.intern()
	1. 字面量：
		- 字符串字面量（如 `"Hello"`）  
		- 基本类型常量（如 `final int MAX = 100;`）  
		- 其他字面量（如 `3.14F`）
	2. 直接引用：指向方法区中类、字段或方法的内存地址或偏移量。
	3. 符号引用：存储在class文件的常量池中，如类名、方法名、字段名等
## 2. 垃圾回收算法
### 判断对象是否可回收
JVM采用可达性分析算法，判断对象是否可回收，从GCroot出发，不可达的对象的可回收
### GCRoots
1. Java虚拟机栈中的局部变量;
2. 方法区中的静态变量和常量
3. 本地方法栈中 JNI引用的对象
4. 活跃的线程对象
5. 被同步锁持有的对象；
6. Java 虚拟机内部的引用：异常对象，系统类加载器
### 回收算法的类型
1. 标记-清除算法：遍历 2 次堆内存，一次标记存活对象，一次回收未被标记对象。
	-  缺点：效率低，遍历2次，还会产生内存碎片;
2. 复制算法：将内存分为2块区域，每次只使用其中一块，标记存活对象后，将其复制到另一块内存；
	-  缺点：内存利用率低，如果存活率高，复制开销大
3. 标记-整理算法：标记后，将所有存活对象向内存空间一端移动，清理边界外的内存；
	- 移动对象和更新指针需要时间，会触发Stop-The-World
4. 分代收集算法
	1. 按照对象存活时间将堆内存分为新生代和老年代，内存占比为1:2，新生代进一步分为Eden区和Survivor区，内存占比为 4：1，Survivor区又分为From和To，内存占比为1：1；
	2. 新对象分配在Eden区，新生代空间不足，触发minorGC，对象从 Eden区复制到Survivor区，之后GC在 From区和To区间复制，每经历一次复制，对象年龄+1，年龄超过阈值，默认为15次，对象晋升到老年代，老年代空间不足，触发majorGC；
	3. 新生代对象存活率低，采用复制算法，老年代存活率高，使用标记清除或标记整理算法；
## 3. 四大引用
1. 强引用：永不回收的引用；
2. 软引用：内存不足时回收；
3. 弱引用：每次GC时会回收；
4. 虚引用：不能直接获取到引用对象，与引用队列搭配使用，用于跟踪对象回收；
## 4. 对象的创建过程
1. 检查类是否被加载
2. 分配内存空间
	- 指针碰撞：内存规整场景
	- 空闲列表：维护空闲列表
	- 通过CAS或TLAB（线程本地分配缓冲)来保证线程安全
3. 初始化零值
4. 设置对象头
5. 执行 init方法，初始化实例变量执行实例代码块和构造方法
## 5. 类的初始化时机
1. 创建类的对象实例，new关键字；
2. 访问静态字段，或静态方法；
3. 反射调用，如Class.forName；
4. 子类被加载时触发父类的加载；
## 6. 类的加载过程
类的加载过程分为，加载、链接、初始化；
1. 加载：将 `.class` 文件的加载到内存，生成 `java.lang.Class` 对象
2. 链接
	- 验证：确保字节码合法且符合 JVM 规范;
	- 准备：为静态变量分配内存并设置初始值（零值）;
	- 解析：将常量池中的符号引用转换为直接引用;
3. 初始化：执行类的 `<clinit>()` 方法，完成静态变量赋值和静态代码块执行。
## 7. 死锁
1. 互斥条件：资源一次只能被一个线程占用，其他线程必须等待；
2. 请求和保持条件：线程在持有一个资源的同时，请求被其他线程持有的资源。
3. 不可剥夺条件：线程已获得的资源在未使用完之前不能被强制剥夺，只能由线程主动释放；
4. 循环等待条件：存在一组线程，每个线程都在等待下一个线程所持有的资源，形成环形等待；
## 8. 线程池
### 参数介绍
1. corePoolSize：核心线程数，处于空闲状态会阻塞等待不会终止的线程；
2. maximumPoolSize ：最大线程数，线程池允许创建的最大线程；
3. keepAliveTime和 unit：非核心线程在空闲状态下的存活时间和时间的单位
4. workQueue： 任务队列，用于保存任务的阻塞队列；
	1. ArrayBlockingQueue 基于数组实现的有界队列；
	2. LinkedBlockingQueue 基于链表实现的无界队列，可以配置容量，默认无界，可设置容量；
	3. SynchronousQueue 同步队列，不存储元素，直接传递；
	4. PriorityBlockingQueue 支持优先级排序的无界队列，任务按优先级执行；
	5. DelayedWorkQueue延迟队列，定时任务执行
5. threadFactory ：线程创建工厂，一般用来指定线程名，优先级，守护线程属性等
6. handler：任务的拒绝策略
	- AbortPolicy：抛出异常
	- DiscardPolicy：静默丢弃
### execute() vs submit()
1. submit返回Future对象，适合需要获取执行结果的任务；execute无返回值，直接在子线程中执行任务；
2. Future对象通过get方法获取返回值或异常，将当前线程关联结点后加入到等待队列中，任务执行完后唤醒，调用时会阻塞调用线程；
### 工作流程
1. 首先判断核心线程数，未超过则创建核心线程执行；
2. 尝试将任务以非阻塞的形式加入到阻塞队列，需要阻塞队列存在容量；
3. 添加失败则判断最大线程数，未超过则创建普通线程执行；
4. 都不满足，则执行拒绝策略
5. 任务执行完，从队列中获取剩余任务执行，当队列为空时，如果线程是核心线程或者处于存活时间内则阻塞等待任务；
### 线程池选择
根据任务类型来选择
1. CPU密集型任务：CPU核心数+1
2. IO密集型任务：CPU核心数的2倍或更高，这个比例根据阻塞比例来定，阻塞比例=阻塞时间/总时间。比如okhttp中分发器默认的线程池大小就是无穷大；
## 9. synchroinzed的实现原理
1. synchroinzed的实现涉及到锁升级的过程；
	1. 对象头中的Mark Word 通过2bits 标记锁的状态和 1bit 标记偏向锁。无锁和偏向锁为 01、轻量级锁00、重量级锁10；
	2. 偏向锁：记录线程ID，同一个线程访问直接验证线程ID，减少无竞争时的锁开销；
	3. 轻量级锁：多个线程交替执行时，创建锁记录，通过CAS操作将Mark Word替换为锁记录指针，失败则自旋，也不存在实际竞争；
	4. 重量级锁：自旋超过阈值或存在多线程竞争时，升级为重量级锁。
2. 重量级锁依赖操作系统互斥量和条件变量实现，线程阻塞和唤醒需通过操作系统内核完成，上下文切换开销大，重量级锁借助Monitor对象管理锁的状态；
	- 对象在进入重量级锁状态时，对象的Mark Word会指向Monitor对象；
	- Monitor对象会记录当前持有锁的线程，锁重入的次数，等待队列（~~竞争失败等待的线程队列以及调用wait方法进入等待的线程队列~~）；
3. 对于同步代码块，生成monitorenter和monitorexit指令包裹代码块，对于同步方法会设置访问标志ACC_SYNCHRONIZED；
	- 线程尝试通过monitorenter指令获取锁，失败进入等待队列等待唤醒。线程执行完毕，通过monitorexit释放锁，唤醒等待队列中线程；

## 10. 锁的分类
1. 乐观锁与悲观锁
	1. synchronized：假设冲突一定会发生，获取资源前先加锁
	2. 乐观锁：CAS操作，先通过原子操作修改数据，失败后重试；
2. 公平锁与非公平锁
	1. synchronized是非公平锁
	2. ReentrantLock 提供公平锁实现，等待队列不为空，才尝试获取锁
3. 独占锁与共享锁
	1. synchronized就是独占锁，只允许一个线程获得锁。
	2. 读写锁中读锁为共享锁；
## 11. yield /wait /sleep/join
1. yield：线程从运行状态Running转为就绪状态Runnable，所有线程包括当前线程都有机会执行，不会释放锁；
2. wait：释放锁并进入等待状态，需要notify或notifyAll唤醒
3. sleep：强制线程休眠指定时间，不释放锁；
4. join：阻塞等待目标线程终止；
## 12. volatile
1. 保证可见性：线程操作变量时，通常会从主内存拷贝到线程的工作内存，volatile修饰的变量修改后立即同步到主内存；
2. 保证有序性：通过插入内存屏障，禁止指令重排序，在单例模式的双重检查锁定实现中就利用了这个特性；
	1. 分配内存空间
	2. 初始化对象（调用构造函数）
	3. 将引用指向分配的内存地址
3. 不保证复合操作的原子性如i++；
## 13.  Hashmap的实现原理
1. 底层的数据结构为数组+链表+红黑树，数组中存放的Node元素，称为桶。
	1. put时根据key的hash值计算索引，计算前先右移16位异或，让hash 值全部比特参与运算。
	2. 发生hash冲突时，同一个桶内的元素通过链表存储，当链表长度超过8而且数组长度超过64，将链表转换为红黑树，红黑树节点小于6时退化为链表；
2. 数组的长度默认为16，负载因子为0.75，容量超过数组大小`*`负载因子进行扩容
	- 每次按照2的倍数进行扩容，保证根据hash计算索引时不存在空间浪费（(n-1)&hash）
3. 不能保证线程安全
	1. Java8之前的头插法会有死循环产生 ;
		1. A->B, T1先迁移A，记录下一个元素B，如果下一个线程开始迁移并完成，那变成了B-A；
	2. Java8之后，多线程put会有覆盖的风险；
### 13.1. ConCurrentHashmap
1. put 元素时，如何保证线程安全
	1. 首次 put时，初始化大小为 16 的数组 ，通过cas操作属性sizeCtl保证只有一个线程进行初始化；
		- sizeCtl <0  则Thread.yield() 
	2. 后续 put时，如果不存在hash冲突，直接cas操作放入元素，存在冲突则synchronized加锁，保证线程安全；
2. put 后如果长度超过阈值或者 put 时，正在扩容，则将当前线程加入到扩容线程中；
	1. 扩容时，首先创建一个容量为之前 2 倍的数组；
	2. 每个线程负责复制一部分的桶，最小长度为 16
	3. 从范围内最后一个桶开始迁移，将迁移成功的桶设置ForwardingNode，其 hash 值为-1；
	4. 扩容完成，用新数组替换之前的旧数组；
## 15. StringBuffer vs StringBuilder
1. StringBuffer是线程安全的，所有公开方法都使用synchronized关键字修饰，而StringBuilder不是线程安全的。
2. 在性能上，由于StringBuilder没有同步开销，所以在单线程环境下性能比StringBuffer好。
## 16. == 与 equals 的区别 hashCode 与 equals 的关系
1.  == 运算符，作用于基本类型，比较的是值，作用于引用类型，比较的是对象内存地址；
2. equals比较的是对象内容，默认实现与== 相同；
3. hashCode返回对象的hash码，用于hash 表的数据结构，默认返回对象的内存地址；
4. 对象在重写 equals 与hashCode方法时要遵循 1个规则
	- 2 个对象的 equals为 true，那它们的 hashcode 一定相同， 反之hashcode 相同， equals 不一定为 true（~~存在 hash 冲突的场景）~~；

## 19. 如何保证线程安全
1. 多线程不安全主要有 3 个原因：
	1. 线程执行顺序的不可预测性（CPU时间片轮换）、
	2. JVM内存模型的特点：线程在访问共享变量时会拷贝一个副本到工作内存中；
	3. 指令重排序；
2. 分别对应了原子性， 可见性，有序性，维护好这 3 个特性就能保证线程安全
	1. 原子性：一个或多个操作要么全部执行完，要么都不执行；
	2. 可见性：一个线程修改了共享变量，其他线程能立刻看到；
	3. 有序性：程序按照代码的先后顺序执行；
3. synchronized： 可以同时保证原子性、可见性和有序性；
4. Lock是 AQS 的子类，和synchronized一样但比它更灵活；
5. volatile： 只能保证可见性和有序性，但不能保证原子性；
6. 原子类：通过CAS（Compare-And-Swap）操作来保证单个变量的原子性；
### 20.线程的状态
1. 在 Java 层面线程的状态有 6 种：
	1. NEW（新建）
	2. RUNNABLE（可运行）
	3. BLOCKED（阻塞）：等锁
	4. WAITING（等待）调用了 wait 和 join方法等待其他线程执行完成
	5. TIMED_WAITING（超时等待）：等待特定时间后执行；
	6. TERMINATED（终止）
2. 在 perfetto trace 中
	1. Running (运行中)线程正在CPU上执行任务。
	2. Runnable (可运行)线程已准备好运行，正在等待CPU调度。
	3. Sleeping (休眠中)线程因等待条件（如互斥锁、sleep操作）而暂停。
	4. Uninterruptible Sleep - IO Block (不可中断睡眠-IO阻塞)线程因等待存储IO等操作而休眠，长时间停留可能引起卡顿。
	5. Uninterruptible Sleep (non-IO) (不可中断睡眠-非IO)线程因IO以外的原因处于不可中断的睡眠状态。
### 21.为什么说反射的性能很差？
1. 直接的调用方法，编译器在编译期就已经确定了方法的具体地址（或在方法表中的偏移量），反射调用需要根据运行时的方法名和参数去在查找类的元数据进行匹配；
2. 反射在编译器还不能确定将要调用哪个方法，绕过了JIT 对热点代码的优化，比如方法内联；
3. 反射时调用的方法参数或者返回值都是 Object 类型，实际如果使用的 基本数据类型，涉及自动拆装箱会带来额外安全检查导致的性能开销；
## 21. AQS
1. 用 volatile修饰 的int值（state）：用于表示锁的状态。0表示空闲，>=1 表示被占用和重入的次数。通过 CAS操作进行修改；
2. CLH 队列锁的变体实现：通过双向链表实现的队列锁，获取锁失败的线程会被封装 Node 加入的队列末尾。通过`LockSupport.park/unpark` 来进行线程的阻塞和唤醒
3. 以ReentrantLock的公平锁实现来介绍 AQS工作流程
	1. `tryAcquire` 检查队列中是有等待节点，没有则获取锁成功，失败，则创建 Node 通过casTail加入到队列末尾；
	2. 开启循环检查当前节点是否等待唤醒的第一个节点（~~检查当前节点的前驱节点 (`node.prev`) 是不是头节点 (`head`~~)），成功则通过tryAcquire再次请求获取锁；
	3. 失败，则调用LockSupport.park阻塞等待；
	4. 释放锁时，遍历队列，获取首个等待线程，通过LockSupport.unpark唤醒；
## 22. 为什么匿名内部类访问的局部变量要用final修饰
1.  局部变量会在方法执行结束时销毁，而匿名内部类对象存储在堆中生命周期更长；
2. 为了解决生命周期不同步的问题，匿名内部类会在内部类创建一个同名字段拷贝局部变量的值；
3. 使用final修饰是为了保证局部变量和副本的值一致；

		 1. CPS转换：挂起函数经过编译后，会为函数增加一个续体类型的参数，续体接口~~Continuation~~最常见的2个方法为invokeSuspend和resume，invokeSuspend挂起协程，执行函数业务，当函数执行完，resume接受函数的执行结果，恢复协程, 此时续体的作用与 Callback 类似；
		 2. 状态机： 除了新增一个续体参数外，还会在函数内新建匿名续体，作为状态机来记录每个挂起点的状态，每个子挂起函数对应一个挂起点。执行子挂起函数，进入挂起点前，状态+1，执行完后调用续体的resume方法，恢复挂起函数的执行，进入下一个状态，直到函数返回。
2. 第二个概念就是结构并发
	 1. 通过层级化的作用域和父子关系来管理协程的生命周期，确保所有并发任务都能被正确完成、取消和异常处理。核心实现由 Job 对象完成
	 2. Job：表示一个协程任务，启动协程会返回Job。
		1. Job 的生命周期包含：
			1. New：协程已创建但未启动（例如通过 `launch(start = CoroutineStart.LAZY)`）。
			2. Active：协程正在运行（默认状态）。
			3. Completing：协程已执行完毕，但可能仍有子协程在运行。
			4. Completed：协程及其所有子协程均已完成。
			5. Cancelling：协程正在取消（例如调用了 `cancel()`）。
			6. Cancelled：协程已取消。
		2. Job提供操作父子Job接口来管理父子协程。父 Job 取消时，所有子 Job 自动取消，子 Job 的异常默认行为会传播到父 Job。
			1. 常见的SupervisorJob，就空实现了childCancelled方法，不处理子协程的取消消息。
### 1.1 CoroutineScope
CoroutineScope协程作用域: 它是协程启动器，作用是启动一个协程；它持有的协程上下文，默认包括Job和协程分发器，
1. 在协程体中启动其他协程都会是它当前作用域的子协程，默认共享父协程的分发器。
2. 常见的作用域
	1. viewModelScope = Dispatchers.Main.immediate+SupervisorJob
		- 当ViewModel被清除时（Activity 或 Fragment被销毁）取消，
	2. Lifecycle.coroutineScope= SupervisorJob() + Dispatchers.Main.immediate
		- 在 Activity onDestroy 时调用 cancel
### 1.2 CoroutineDispatcher
CoroutineDispatcher协程的分发器:本质是一个线程池或者一个特定的线程 Handler，将续体的执行调度到指定线程上。系统提供的分发器有 4 种：
1. Dispatchers.Default：线程数与 CPU 核心数相关，为 CPU 密集型任务设计；
2. Dispatchers.IO：可动态扩展线程数，默认为64个，为IO 密集型任务设计；
3. Dispatchers.Main：指定 主线程（UI 线程） 执行任务
4. Dispatchers.Unconfined：不限制协程的线程，启动时在调用者线程执行，恢复时可能切换到其他线程。
### 1.3  CoroutineContext 
CoroutineContext 用来保存协程上下文的自定义集合，重写了 plus操作符，通过 key 做唯一标识，采用链表的数据结构，并保证分发器在链表头；
1. 上面提到的CoroutineDispatcher和 Job 都是协程上下文元素的一种，其他常见的还包含CoroutineName:指定协程名 和 CoroutineExceptionHandler协程的异常处理器；
### 1.4 协程与线程的对比
1. 线程由内核完成调度，切换成本和内存开销大，生命周期管理困难；
2. 协程是一种构建在用户空间轻量级的线程操作框架，核心概念为非阻塞式的挂起与恢复与结构化并发，适合与 IO 密集型任务；
3. 协程不是线程，而是运行在线程上的任务，一个线程可以运行成千上万个协程
4. 举一个例子：子线程执行任务通知主线程
	1. 线程的做法是采用 join 阻塞等待执行结果；
	2. 启动运行在主线程的协程后再启动一个子线程协程获取执行结果；
## 2. 协程的异常和取消
1. 从启动协程的过程说起，通过 launch或 aync 启动协程时，方法中传入的lambda为CoroutineScope的挂起扩展函数，启动一个协程从语义上来说是创建一个续体并 在指定的协程分发器内调用其resume方法；
2. 创建的续体为BaseContinuationImpl的子类，在它的resume方法中，无论是正常运行的业务返回值，还是异常或取消的结果都统一封装为 Result对象后返回。
3. 当协程执行完，通过续体通知所有父协程，根据Result的类型判断是异常还是取消还是正常完成；
4. 在复杂业务中通过SupervisorJob隔离子协程异常 同时 指定CoroutineExceptionHandler捕获子协程异常，统一上报；
## 3. Flow的实现原理
 Flow 是构建在协程之上的一个响应式编程框架，继承了协程的 2 个特点
	1. 借助挂起函数实现的无阻塞式的挂起与恢复；
	2. 结构化并发：与当前协程作用域的生命周期绑定，父协程取消时，子任务也会取消，~~比如 Flow 上发射的数据~~；
### 3.1 背压的策略选择
1. buffer： 指定缓冲区大小，默认值为 64
2. conflate： 合并，保留最新一个生成的元素
3. collectLatest：中断消费者的消费过程，消费者处理最新值
4. sample 定期地从数据流中抽取一个最新的数据出来进行处理，忽略两次取样之间的所有数据
5. debounce()在数据流停顿的指定时间后，才发出最后一个数据|
### 3.2 背压 buffer 的实现原理
1. 背压是指生产者的生产速度大于消费者的消费速度；
2. 在 Java 世界中如何处理这种情况：设置一个缓存池，分别将生产者和消费者放在不同的线程，生产者就不用等待消费者；
3. 同理在 Flow 中，借助协程机制和buffer 操作符，做到只挂起而不阻塞线程，实现原理依赖于 Kotlin 协程的Channel。
	1. 调用 buffer 后，会在当前协程作用域内启动一个子协程，创建指定容量的 Channel 并返回；
	2. 该 Channel 有 2 个作用
		1. 封装成对应的收集者收集上游数据并缓存，当数据发射完毕时，结束协程，关闭 Channel;
		2. 同时作为发射者，开启循环发射数据给下游收集者，无数据时则挂起等待；
### 3.3 冷流与热流
1. Flow 分为冷流与热流
	1. 冷流必须有要指定收集者才会开始发射数据~~冷流会为每个收集器创建一个新的数据流，只有在开始收集数据时，才发射数据，这一点与 rxjava一样，主要用于数据库加载信息和网络请求等场景~~；
	2. 热流是主动运行，无论是否有收集器都会持续发送数据；
2. 热流分为 SharedFlow与 StateFlow
3. 简单介绍在 SharedFlow的源码实现
	1. 在 SharedFlow 内部存在 2 个数组
		1. 一个数组用于缓存数据和 Emitter 对象，Emitter 对象封装了数据发射时所在协程的续体，是在挂起缓存策略下超过缓存容量的数据形式；
		2. 另一个数组用于缓存封装了当前收集者所在协程续体的 Slot 对象；
	2. 默认的的缓存策略是挂起，
		1. 当发射数据时
			1. 首先检查是否有收集者，没有则根据回放容量大小，缓存最新数据；
			2. 缓存数据超过缓存容量同时收集者未能及时处理数据，执行挂起逻辑，创建 Emitter 对象 加入到缓存数组中；
		2. 收集数据时
			- 创建 Slot 对象加入到Slot 数组中，根据回放索引从缓存数组中获取数据，获取失败则挂起等待。
4. SharedFlow 会广播一连串的事件，StateFlow 只会持有和广播一个 当前状态。StateFlow 是 SharedFlow 的一种特殊配置，缓冲大小为 0，回放个数为 1，缓冲策略为 Lastest，只保留最新值，通常用来替换 LiveData，来作为 UI状态的“单一数据源”；
### 3.4 Kotlin Flow 如何与 LiveData 互操作
1. flow.asLiveData()
	- 默认在 `Dispatchers.Main` 上收集
2. liveData.asFlow()
	- 转换得到的是冷流
	- 使用 `observeForever` 监听数据变化

}

## 4. async与launch的区别
1. async与launch都是协程启动器，区别在于他们的返回值，launch返回Job,async返回Deferred；
	1. Deffered是Job的子类，除了可以控制协程的生命周期，还可以通过await获取协程的返回值；
	2. launch的异常会立即传播，而async的异常被封装在Deferred，只有调用await时才会抛出
2. await是一个挂起函数，Deffered是Job子类型，当await被调用时，如果当前Deffered状态已经完成，直接返回结果，如果没有完成，则调用invokeOnCompletion 新建一个子Job加入到Deffered，用来监听Deffered的完成状态。
### 4.1 withContext
1. 调用~~suspendCoroutineUninterceptedOrReturn~~挂起当前协程， 运行指定的拦截器执行任务，任务执行完恢复当前协程的执行；
2. async与launch都是协程启动器，作用是启动一个协程，它们都可以并发执行多个任务，其中async可以通过 await 获取返回值，而withContext会挂起当前协程等待任务执行完，只能串行执行任务，withContext 可以直接获得执行结果；
### 4.2 Kotlin 协程调度器切换流程
1. 分发器是CoroutineDispatcher对象， 它包含一个线程池或者特定的线程 Handler，同时也是协程上下文的子类； 
2. 协程内置了 4 种分发器
	1. Dispatchers.Default：为 CPU 密集型任务设计；
	2. Dispatchers.IO：为IO 密集型任务设计；
	3. Dispatchers.Main：主线程，执行 UI 操作
	4. Dispatchers.Unconfined：不限制协程的线程，
3. 分发器通过 withContext 切换或者在 launch 和async 中指定；
4. 续体通过intercepted 方法与分发器组合生成ContinuationInterceptor对象，指定续体的 resumeWith和 invokeSuspsend 方法调用线程完成调度；

## 6. inline/noinline/crossinline 
1. inline：函数对象在编译后会转换为对应的Function 对象，inline用来修饰函数会将函数参数的方法体内联到方法调用处减少对象的创建开销；
	-  inline 的缺点：每个调用点都会复制内联函数的代码，可能导致代码膨胀
2. noinline 用来修饰函数参数，作用禁用内联，使用场景主要是当内联函数的函数参数需要作为参数进行传递。
3. crossinline 用来修饰函数参数，内联函数可以被函数参数 中 return 语句退出，crossinline禁用全局返回，表现和非内联函数一样。
4. inline 的使用场景
	1. 当函数是高阶函数
	2. 避免函数调用的开销
	3. 支持非局部返回

## 2. Handler消息机制
1. Handler消息机制涉及3个对象
	1. Looper：轮询器，循环从消息队列中取消息，每个线程只有唯一的轮询器，
	2. MessageQueue：消息队列，保存消息，数据结构是一个单向链表，节点按照消息的执行时间进行排序;
	3. Handler：向消息队列发送消息，同时处理消息返回结果，同一个线程可以有多个Handler;
2. Looper通过ThreadLocal来保证同一个线程只初始化一次，主线程的Looper在应用启动时由系统创建，子线程需要手动创建并开启轮询，结束后退出轮询；
3. MessageQueue存在2种特殊消息，称为同步屏障和异步消息来完成 View 的绘制；
	- 当Choreographer接受到V-SYNC信号后，调用ViewRootImpl执行sheduleTraversals 绘制View时会发送这2个消息
		- 同步屏障消息关联的Hanlder为空，异步消息的异步属性为true
	- 消息队列在遍历到同步屏障后，优先查找队列中的异步消息执行，执行View的绘制操作，直到ViewRootImpl 发送消息移除屏障；
4. MessageQueue还提供IdleHandler接口，当消息队列为空是或者消息进入等待，会执行IdleHandler的queueIdle方法，常见的用于在 UI 线程空闲时执行非紧急任务，如日志上报，数据预加载等来减少首帧数据的卡顿。
5. ThreadLocal实现原理和内存泄露
	1. 实现原理：
		1. 通过线程唯一的ThreadLocalMap，存储对应的ThreadLocal和Looper键值对；
		2. 其中ThreadLocal是Looper的final静态属性，保证全局单例；
	2. ThreadLocalMap中Key为ThreadLocal包装的弱引用，Value强引用：Key被回收后，Value成为“幽灵数据”无法自动清理，需要手动移除
6. 为何loop()方法是死循环却不会占用cpu时间片
	- MessageQueue.next()方法在空闲时会通过Linux的`epoll`机制进入休眠状态，让出CPU时间片。
7. 为何next()方法阻塞却不会卡死。
	- 卡死指的用户输入无响应，Android应用程序就基于事件驱动的，用户输入，UI 绘制都是通过主线程的Handler 处理。
8. Handler post(Runnable) 如何把 Runnable 包装成 Message？
	- 从消息池中取一个消息，将它的callback指定为runnable，执行到此消息时先运行此callback;
## 3. 点击事件的传递机制
1. 一个事件序列由一个Down事件，多个Move事件，一个up或cancel事件组成；
2. 事件的传递顺序：依次从Activity到PhoneWindow到DecorView 到ViewGroup再到View；
3. 处理流程由3个核心方法组成：
	1. onInterceptTouchEvent：ViewGroup方法，判断是否拦截事件，默认为false;
	2. dispatchTouchEvent：ViewGroup中负责分发事件，View中会直接调用onTouchEvent处理；
	3. onTouchEvent：处理事件，返回true，代表消费事件;
4. 当ViewGroup接受到Down事件后
	1. 判断是否拦截；
	2. 如果不拦截，则遍历子View，寻找处理此事件的View
		1. 如果View的onTouchEvent或者onTouchListener返回true，将其保存在ViewGroup中；
		2. ViewGroup通过链表来保存处理Down事件的子View，对于单指触摸事件，链表中只会有一个元素；
		3. 后续的其他事件先判断是否拦截，但不会在遍历子View，而是直接使用链表中保存的子View处理点击事件；
	3. 如果一个子View，不处理Down事件，也不会接收到其他事件；
### 3.1 cancel事件如何产生
1. 异常情况导致上一次事件序列还未结束，下个Down事件又到达，cancel通知子View
2. 子View接收到DOWN事件后，设置了PFLAG_CANCEL_NEXT_UP_EVENT;
3. 父View下发了Down事件，但是拦截了后续的事件；
4. View在处理事件过程中被父View移除；
### 3.2 常见的滑动冲突解决
1. 外部拦截法：父View根据条件判断是否拦截；
	- 比如ViewPager嵌套ListView场景，在ViewPager的`onIntercepetorTouchEvent` 方法中根据Move方向进行拦截，ViewPager处理横向滑动，ListView处理纵向滑动；
2.  内部拦截法：子View通过requestDisallowInterceptTouchEvent 控制父容器是否拦截，比如ViewPager嵌套水平滑动的RecyclerView，重写RecyclerView的dispatchTouchEvent方法，滑动RecyclerView的边缘时在允许父View进行拦截翻页；
3. 这2个方法的前提，都是父View不能拦截Down事件；
## 4. Actvity的启动模式
1. standard(默认模式)：每次启动Activity都会创建新实例，无论是否已存在
	- 应用场景： 需要多次打开的同一页面，如设置页；
2. singleTop(栈顶复用)：若目标Activity已位于栈顶，则复用该实例，触发onNewIntent，否则新建实例。
	- 应用场景：防止重复启动同一页面的场景：如通知跳转的落地页；
3. singleTask（栈内单例）：在任务栈中仅存一个实例。启动时,若存在该Activity的实例，则清除上方所有的Acitivity，使其位于栈顶，触发onNewIntent
	- 应用场景：需要保证唯一性，如应用的主页；
4. singleInstance(全局单例)：Activity独占一个任务栈，且该栈仅存此实例。其他的Activity默认放入其他栈；
	- 应用场景：系统功能界面，如拨号盘等；
## 5. DecorView与ViewRootImpl的关系
1. DecorView是窗口的顶级视图容器，每一个Activity或Dialog都对应一个DecorView;
2. ViewRootImpl 是DecorView 与 WMS的桥梁，控制DecorView的整个生命周期，包括创建、测量、布局、绘制以及事件分发；
## 6. Serializable vs Parcelable
1. Serializable是Java标准接口，适用于需要将对象存储在本地文件或进行网络传输的场景，使用反射机制，序列化和反序列化过程需要大量I/O操作，效率较低；
2. Parcelable是Android专有，适用于组件间传递数据，基于内存设计，效率较高，使用时需要手动控制序列化字段比Serializable复杂；

- 计算机领域通用的Socket\文件共享\共享内存，以及 Android 特有的 Binder 通信和在 Binder 基础上提供的 Intent,Messenger,AIDL和 ContentProvider等
## 8. Binder
### 8.1 mmap
1. 由于进程隔离，用户空间与用户空间要进行通信，必须要通过内核空间，客户端首先将数据拷贝到内核空间，再从内核空间拷贝到服务端，传统的通信方式都会拷贝 2 次；
2. 在binder通信中，服务端启动时，会先调用mmap将服务端用户空间的一端虚拟内存和内核空间的一段虚拟内存，映射到同一块物理内存上；
3. 这段物理内存作为一个缓冲区，客户端发送数据时，内核会通过copy_from_user将数据放到缓冲区，然后通知服务端。服务端只需要通过用户空间相应的虚拟地址，就能直接访问数据，这个就减少了一次内存拷贝；
### 8.2 架构设计
1. Binder采用C/S架构和分层设计，在应用层，framework层，native层，内核层，客户端和服务端分别持有不同的binder对象；
	1. 应用层，客户端持有服务代理，服务端实现具体服务;
	2. 在framework层，客户端对应BinderProxy对象，服务端对应Binder对象;
	3. 在navite层客户端对应BpBinder，服务端对应BBinder;
	4. 在内核层，客户端对应binder_ref，服务端对应binder_node;
2. binder对象在内核中传递时，会在客户端和服务端生成对应的binder_ref和binder_node，binder_ref指向binder_node并通过句柄handle访问，对于实名服务，如AMS，WMS 通过句柄0进入service_manager查询，对于匿名服务，在传递binder对象时，记录动态句柄。
### 8.3 常见问题
1. oneway与非oneway的区别
	1. oneway方法属于异步调用，客户端立即返回，不阻塞，方法也不允许有返回值
2. 最大线程数
	1. 主线程+15个子线程；
3. Binder 和其他进程间通信方式相比的优点
	1. 性能：一次数据拷贝
	2. 安全行：UID/PID权限校验
	3. 易用性：基于 C/S 架构设计，客户端通过代理形式直接使用服务端接口方法；
### 8.4 AIDL
1. AIDL的全称是Android Interface Definition Language，即 Android 接口定义语言，作用是实现 Android 的跨进程通信。
2. SDK 中 aidl 工具会将 aidl 文件编译成 Java 接口文件，文件中包含：
	1. 接口本身
	2. `DESCRIPTOR`：描述Binder 的唯一标识符，通常是接口的全限定名。
	3. Transaction Codes：每个方法的唯一编码；
	4. Stub 存根类
		- Stub实现了接口同时继承 Binder， 重写了asInterface，onTransact，asBinder3 个方法；
		- asInterface是查询接口，如果客户端和服务端属于同一个进程，返回 Stub 对象，否则返回代理；
		- `asBinder`返回 Stub 本身
		- `onTransact`，处理客户端调用的入口，根据 Code路由到正确的方法；
		- 服务端需要 继承 Stub 类，并实现具体的服务的方法；
	5. Proxy 代理类， 代理了BinderProxy对象，它是Binder服务在客户端应用层的表示对象。代理类负责将请求参数写入 Parcel 和从Parcel从读取返回值。
3. 支持的数据类型
	- 基本数据类型（`int`, `long`, `char`, `boolean`, `double` 等）
	- `String`
	- `CharSequence`
	- `List` (其中的元素必须是 AIDL 支持的类型)
	- `Map` (其中的元素必须是 AIDL 支持的类型)
	- 其他 AIDL 接口
	- 实现了 `Parcelable` 接口的自定义对象
4. `in`, `out`, `inout` 关键字：用于修饰方法的参数，表示数据的流向，对于非基本数据类型，正确使用这些关键字可以优化性能，避免不必要的数据拷贝。
    - `in`（默认）：数据从客户端流向服务端。
    - `out`：数据从服务端流向客户端。
    - `inout`：双向流动。
## 9. RecyclerView 
### 9.1 如何设计一个高性能的滑动列表
1. 数据层面
	1. 借助DiffUtil来实现数据的差异化更新;
	2. 使用分页加载，实现滚动预加载，避免一次性加载过多数据；
	3. 对于频繁来回滑动或布局复杂的场景，增加cacheView 的缓存大小；
2. 视图层面
	1. 减少布局嵌套避免过度绘制，合理使用 Merge 标签和约束布局，Merge标签会合并子View中的控件到父布局中，减少一层嵌套；
	2. 通过 ViewHolder记录子 View，减少 findViewById的开销；
	3. 如果 item 的尺寸固定，可以设置固定大小避免重复测量；
	4. 避免在onCreateViewHolder 和onBindViewHolder创建工具类对象，比如点击监听；
3. 内存与性能层面
	1. 及时释放资源，避免泄漏
		- 在Adapter的onViewRecycled中取消图标加载，清理动画，释放资源在onViewDetachedFromWindow时清除图片；
	2. 列表滚动时暂停图片加载；
### 9.2 如何优化列表大图滑动
1.  减少图片的内存占用，
	1. 限制图片的实际尺寸，选择合适的Bitmap 格式
	2. 主动回收资源：在onViewRecycled和onViewDetachedFromWindow清除图片
	3. 这2 项都可以借助Glide 图片加载框架实现
2. 滑动性能优化
	1. 设置滑动监听，滑动时暂停图片加载，停止滑动时恢复；
	2. 数据分页加载，设置预加载阈值；
3. 监控内存使用情况和性能指标，及时调整策略
	1. 对于内存，跟随onTrimMemory回调进行内存清理；
	2. 性能方面设置 Choreographer FrameCallback检测丢帧率；
### 9.3 RecyclerView的缓存机制
分为 4 级缓存
1. changedScrap/attachedScrap：临时存放仍在当前屏幕可见、但被标记为移除或重用的列表项
	1. changedScrap：调用了notifyItemChanged、notifyItemRangeChanged这一类方法，通知列表项数据发生变化。
		- 数据发生变化后，重绘前先把之前的列表缓存;
	2. attachedScrap：notifyItemMoved、notifyItemRemoved这种列表项发生移动，但列表项数据本身没有发生变化的场景。
		- 移除了一个 item，视图重建前，先将 所有 item 缓存到attachedScrap中，重建时再根据对应 position 找到 ViewHolder 对象复用;
2. cachedViews主要用于存放已被移出屏幕、但有可能很快重新进入屏幕的列表项，默认大小限制为2；
3. ViewCacheExtension:提供额外的、可由开发人员自由控制的缓存层级;
4. recyclerPool：按不同的itemType分别存放超出mCachedViews限制的、被移出屏幕的列表项
	1. 以SparseArray区分不同的itemType，每个itemType又通过ArrayList保存ViewHolder对象，每种itemType的ArrayList大小限制默认为5；
### 9.4 RecyclerView 预加载下一页数据时机
- 基于滚动位置的检测，设置滚动监听和预加载阈值，当向下滚动时，当剩余的 item小于阈值则触发加载；
### 9.5 SparseArray
1. 用来替换键值为基本数据类型的的map的数据结构；
2. 以SparseIntArray为例，内部数据结构为 2 个数组，Int 数组用于存储 key 值，对象数组存储 value；
3. put时 通过二分查找key值对应索引；
	1. 如果索引已存在，则替换当前值
	2. 如果索引对应值为删除，则重用删除位置
	3. 如果索引还在当前数组范围，则移动数组位置插入，否则扩容；
4. 删除时，只将 value标记为 Deleted，put 时检测删除标记，执行实际的删除操作；
5. 对数据大小小于1000数据集内存效率比Hashmap 高；
### 9.6 ItemDecoration
1. onDraw: 在Item绘制之前调用，用于绘制装饰效果，这些效果会被Item的内容覆盖。
2. onDrawOver 在Item绘制之后调用，用于绘制装饰效果，这些效果会覆盖在Item的内容之上。
3. getItemOffsets: 用于设置Item的偏移量，用于留出分割线的空间。
## 10. Activity的启动流程
1. 以Launcher冷启动应用为例
	1. 启动一个Activity涉及4个进程：Launcher进程，AMS所属的system_server进程，zygote进程，应用进程；
	2. 2种IPC方式：socket通信和Binder通信；
2. Launcher进程判断是否需要处理 `ActivityResult`后，获取AMS的服务，启动Activity；
3. AMS解析Intent参数，进行权限校验， 判断应用进程不存在，通过socket请求zygote创建应用进程，zygote fork出子进程后，通过反射创建ActivityThread对象，同时执行其入口main方法；
4. 在main方法中，启动应用的Binder服务ApplicationThread ，并返回给AMS，同时启动主线程Looper，开始消息循环；形成AMS -> ApplicationThread ->Handler通信链；
5. AMS会调用ApplicationThread的bindApplication方法，向主线程中发送bindApplication消息，启动Application；
6. 对于Activity的相关生命周期方法，则封装成对应事务后，统一发送EXECUTE_TRANSACTION消息进行处理;	
7. 当执行到 onResume 时，会调用`WindowManager.addView` 方法，将 `DecorView`添加到 `WindowManager` 中。触发 View 的测量、布局、绘制流程，此时 Activity 才对用户可见；
## 11. Android系统启动流程，init进程的作用？/Android启动过程，从按下电源到应用启动？
1. Android系统底层基于Linux Kernel, 当Kernel启动后会创建init进程；
2. init 进程是所有用户空间进程的鼻祖，启动后执行 main 方法，分析并运行所有的 init.rc 文件，启动servicemanager, Zygote进程
3. servicemanager是 binder 服务管家，常见的系统实名服务 AMS，PKMS，WMS 等通过对应服务名保存在servicemanager中；
4. Zygote 进程是 Java 进程的鼻祖，启动后，通过fork创建system_server进程， AMS，PKMS，WMS 等系统服务真正运行的进程；
5. 同时Zygote还会建立socket通道，作为通信的服务端，用于响应客户端创建进程的请求；

## 14. 插件化
插件化就是通过动态加载apk文件来实现功能更新和扩展，一个apk文件至少包含dex文件/资源文件/so文件/manifest文件，插件化原理也可以分为4部分。
1. 加载dex文件
	1. dex文件是class文件的集合，加载时同样遵循双亲委托机制;
	2. 在Android中存在2中ClassLoader,
		- BootClassLoader 加载系统类，
		- PathClassLoader负载加载应用类,PathClassLoader的parent属性会指向BootClassLoader；
		- PathClassLoader通过 dex 文件路径进行加载，加载完成后，将class数据保存在 dex 数组中；
	3. 插件化加载dex文件的流程：通过自定义ClassLoader，将 parent 指向PathClassLoader，以插件文件路径形式加载插件中dex文件生成 dex 数组，然后与主App中PathClassLoader的dex数组进行合并，合并之后通过反射访问插件中的类；
2. 加载so文件
	Android中存在2中加载so的方式
	1. System.loadLibrary：以相对路径形式加载apk中预置的so;
	2. System.load:指定so文件的绝对路径进行加载；
	3. 插件化通过第二种方式进行加载；
3. 加载资源
	1. 与主app的资源进行合并后，正常通过id进行查找即可；
	2. 资源的查找是通过Context 调用到AssetMananger，它是以资源文件路径形式进行初始化，并提供接口添加更多的资源路径，我们只需要解决资源ID的冲突问题即可。
	3. 冲突是因为资源ID是一个32位的16进制数
		1. 1个字节的包段：标识资源所属的包，01为系统资源，7f为应用资源；
		2. 1个字节的类型段：标识资源类型，如layout,string,drawable;
		3. 2个字节的条目段：标识资源具体的编号
	4. 插件apk与主apk资源如果按照正常方式打包，包段相同，就可能会存在资源冲突，最简单的解决方法就是通过自定义gradle的Transform修改资源ID的包段； 
4. 加载插件中的Activity、Service等组件，通过代理 Activity和 Hook AMS /ActivityThread 方案实现。以启动插件中的 Activity 为例：
	1. Activity的启动前会先校验Activity是否在manifest中注册，而插件Activity不能预先注册，所以要想启动插件Activity，启动前要将插件Activity信息替换为已注册的代理Activity通过校验，校验完成之后将代理Activity替换为插件Activity；
	2. hookAMS：通过动态代理AMS，拦截startActivity方法，将intent中的插件 Activity信息替换为代理Activity;
	3. hookActivityThread中主线程的Handler，~~拦截code为159的~~启动Activity 消息，通过 messge中携带的插件Activity信息，将intent替换为插件Activity;
5. 以上是插件化的基本实现原理，我在实践中遇到的问题是：
	1. 由于系统的Namespace 机制（so 只能访问到相同 ClassLoader下的 so），插件中的so无法访问已加载的so库比如 liblog 这种基础 so 库；
	2. Tinker 思想：替换所有的 ClassLoader，重新加载所有的 so，将 插件so拷贝到 ClassLoader 的 nativeLibraryPathElements数组中；
	3. ReLinker 的思想，so文件遵循 elf 格式，解析插件so 文件的.dynamic字段，获取所有依赖so 的路径，通过System.loadLibrary在重新加载一次；
	4. ~~社会工程学；~~
### 14.1 Tinker
1. Tinker 通过替换 ClassLoader 的方法重新加载整个应用的类来解决混合编译的问题，带来的新问题就是 Application是有系统加载的，应用来不及替换加载它的 ClassLoader;

## 15. 插件化换肤 
1. 插件化换肤是指通过从服务端下载主题包，在不重启app的前提下，实现颜色，背景，以及自定义属性的替换；
2. 要实现这个需求，在流程上主要分为2步：
	1. hook应用中View的创建过程，保存支持动态替换的View及其对应的属性；
	2. 创建插件Resource对象，在保证插件与宿主中的资源名称和类型一致的前提下，通过名称和类型从插件Resource中找到对应属性设置给View； 
3. hook应用中View
	1. View是在LayoutInflater解析xml时，通过xml中指定的全类名反射创建；
	2. 在反射时，Inflater提供了一个Hook点，允许应用自定反射过程，比如androidx  中的AppCompatActivity，就会通过这个方法将TextView ，ImageView 替换为AppCompatTextView,AppCompatImageView ；
	3. 参考AppCompatActivity写法，在Activity onCreate前（ActivityLifecycleCallback），替换Inflater的创建方法；
4. 加载插件Resource
	1. 通过Context获取资源时，最终是通过AssetManager方法获取；
	2. AssetManager 允许通过资源的文件路径进行创建;
	3. 这样传入下载的资源包路径就可以创建插件Resource;
5. 在实践中遇到的问题就是，如何修改隐藏API 的问题。
	1. LayoutInflater 虽然提供了接口允许自定义设置创建 View 的工厂，但是通过一个 flag 控制只允许此工厂被设置一次
		1. 在前面提到的流程中，默认Androidx 中的 AppcompatActivity 已经设置了一次。要想自定义这个工厂，需要修改这个 boolean 值，在 Android 10 之前可以直接反射修改，之后，这个值被属性被设置为隐藏 api，不允许应用调用；
	2. 我采用的方案是不修改底层代码，完全基于Java 中Unsafe和 MethodHandle实现；
	3. Unsafe 直接通过访问和修改对象的内存地址来控制属性的访问；
		1. 对象的内存布局：对象头+实例数据+对齐填充，偏移量是相对于对象起始地址的字节距离
	4. MethodHandle是反射API 的一种替代，其artFieldOrMethod字段指向了属性和方法的内存地址，是操作目标类方法和属性的句柄；
	5. 具体的实现流程可以分为 3 步：
		1. 通过 Unsafe 获取 Class 的 Class 对象 iFields 属性的偏移地址，根据此地址得到目标类的iFields属性地址， 此地址可以理解为目标类属性集合的首地址；
		2. 在工具类定义 2 个已知属性，通过Unsafe得到这 2 个属性对应的MethodHandle的artFieldOrMethod地址 ，比较他们的大小，计算出每个属性的大小
		3. 从前面 2 步中，得到了属性集合首地址和每个属性的大小。就可以通过 Unsafe替换已知属性的 MethodHandle的artFieldOrMethod地址为目标属性，通过 MethodHandle 获取属性；

## 1. RxJava
1. RxJava是基于观察者模式实现的一个异步数据流处理框架
	1. Observable（被观察者）：负责发送数据
	2. Observer（观察者）：订阅Observable 并处理数据；
	3. 通过各种操作符实现事件流的转换、组合和过滤；
2. 重点介绍下线程调度操作符subscribeOn和observerOn实现原理
	1. 每个操作符都有一组对应的观察者和被观察者，命名采用类型+操作符的形式比如 map对应ObservableMap和MapObserver,，分别对上游的被观察者和下游的观察者进行装饰，是对装饰者模式的一种应用；
	2. 对于subscribeOn操作符，订阅时直接在subscribeActual方法中指定线程，让上游被观察者对下游观察者进行订阅；subscribeOn特点就是多次subscribeOn，只有靠近数据流最近的调用会生效；
	3. 对于observerOn操作符，在指定线程中调用下游观察者的接受方法如onNext,onError,onComplete接收数据，;同理，多次指定观察者线程，只有离下游观察者最近的才会生效。
	4. 如果subscribeOn指定线程，不通过observerOn切换，观察者也不会回到默认线程；
3. 背压的实现
	1. rxjava 的背压是指在异步场景中，当被观察者发送事件速度快于观察者的处理速度的情况下，一种告诉上游的被观察者降低发送速度的策略；
	2. 基于观察者模式的拉模型实现，观察者通过request 设置拉取数量，控制数据流速；
	3. 同时指定溢出策略：抛出异常、配置更大的缓冲区（默认缓冲区为128）、丢弃事件、保留最新事件等；

## 4. OkHttp

### 1. TCP与UDP

1. TCP：面向连接。 传输数据前需通过三次握手建立连接，结束后通过四次挥手断开连接。UDP：无连接。 直接发送数据，不需要预先建立或断开连接。
2. UDP头部开销更少仅8字节，TCP需要20~60字节，包括序列号、确认号、窗口大小等控制信息；
3. TCP能保证数据不丢失 不重复 按序到达，UDP的数据可能丢失或乱序，但UDP拥有更快的传输速度 实时性更好。
4. 在传输模式上，TCP仅支持一对一通信，UDP支持一对一、一对多、多对多。
5. TCP的应用场景：主要是可靠性要求较高，如网页浏览，UDP适用于实时性优先的场景：如实时视频。
### 2. TCP 三次握手与四次挥手
1. 三次握手
	1. 第一次握手，客户端发送SYN=1的报文，携带初始序列号x，客户端进入SYN_SENT状态；
	2. 第二次握手，服务端收到SYN后，发送SYN和ACK=1的报文，携带自己的初始序列号y，确认号为x+1，服务端进入SYN_RCVD状态
	3. 第三次握手，客户端收到SYN和ACK后，发送ACK=1报文，确认号为y+1，序列号为x+1，客户端和服务端进入ESTABLISHED状态，连接建立；
2. 三次握手的作用
	1. 防止历史重复连接，通过序列号判断是否为历史连接；
	2. 确认双向通信能力，客户端和服务端都要进行一次收发确认；
3. 四次挥手
	1. 第一次挥手，主动关闭方如客户端发送FIN=1报文，~~序列号为u，~~客户端进入FIN_WAIT_1状态，表示不在发送数据;
	2. 第二次挥手，被动关闭方如服务端收到FIN后，发送ACK=1报文~~，确认号为u+1，序列号为v~~，服务端进入CLOSE_WAIT状态，客户端收到后进入FIN_WAIT_2状态，此时客户端到服务端的连接关闭，但服务端仍可发送数据;
	3. 第三次挥手，服务端处理完剩余数据后，发送FIN=1报文，~~序列号为w，~~服务端进入LAST_ACK状态；
	4. 第四次挥手，客户端接受到FIN后，发送ACK=1的报文，~~确认号为w+1，序列号为u+1，~~客户端进入TIME_WAIT状态，等待2MSL后关闭，服务端收到ACK立即关闭；
4. 四次挥手的作用
	1. 全双工关闭：每个方向需独立发送FIN和ACK，被动方可能需要时间处理剩余数据，无法立即发送FIN；
	2. TIME_WAIT的作用
		1. 确保最后一个ACK到达服务端，若丢失，服务端会重传FIN；
		2. 防止旧连接的报文因网络延迟滞留干扰新连接；
5. 为什么握手是三次挥手是四次
	- 握手时，服务端的 `SYN+ACK` 可合并为一次发送；挥手时，被动关闭方的 `ACK` 和 `FIN` 通常无法合并（需处理剩余数据）。
6. 什么是SYN洪水攻击
	- 攻击客户端在短时间内伪造大量不存在的IP地址，向服务器不断地发送SYN包，服务器回复确认包，并等待客户的确认。由于源地址是不存在的，服务器，需要不断的重发直至超时；
### 3. HTTP与HTTPS
HTTP是超文本传输协议，HTTPS是超文本安全传输协议，两者都是通过TCP与服务器建立连接，连接建立后，HTTP直接明文传输数据，HTTPS会在此连接基础上增加SSL/TLS握手，后续采用此次握手生成的会话密钥加密传输数据。
以TLS握手过程为例，简化为4步
1. 客户端请求建立连接，发送支持的TLS版本、加密套件和客户端随机数;
2. 服务响应返回选择的TLS版本、加密套件、服务端随机数和证书，证书中包含主题（域名、组织单位、地点等），签发机构和公钥
3. 客户端验证证书，并用证书中的公钥加密预主密钥（也是一个随机数）返回给服务端；
4. 客户端和服务端 用前面三步中生成的三个随机数生成对称会话密钥用于后续加密通信；
### 4.  一次网络请求的发起过程
1. 输入网址，解析URL，URL结构包含协议、域名、路径和参数~~，协议如HTTP/HTTPS，浏览器会默认补全；~~
2. DNS解析：将域名转换为IP地址
	1. 首先依次检查缓存中是否存在该域名的IP，缓存包括浏览器缓存、系统缓存和路由器缓存；
	2. 如果没有缓存则依次向本地DNS服务器和跟域名服务器查询；
3. 三次握手建立TCP连接，如果为HTTPS则增加SSL/TLS握手;
4. 发送HTTP请求，请求报文结构包含
	- 请求方法GET/POST
	- 请求头如HOST
	- 请求体：POST请求时携带的表单或Json数据
5. 服务端处理请求，返回响应数据，响应报文结构包含：
	- 状态码：如请求成功为200、
	- 响应头：如表示数据类型的Content-type、
	- 响应体：HTML内容或Json数据；
6. 浏览器解析HTML，渲染布局；
7. 四次挥手断开连接或保持连接，复用TCP通道用于后续请求处理；

### 6. 常见的状态码
1. 1开头的代表信息响应
	- 100 Continue：客户端继续发送请求的剩余部分；
2. 2开头的代表成功
	   1. 200 OK：请求成功，响应中包含请求的数据；
3. 3开头的代表重定向
	- 301 永久重定向、302临时重定向：资源被移到新的URL，客户端接下来会用新的URL发起请求，浏览器会缓存永久重定向；
	- 304：资源未修改，客户端可使用本地缓存，搭配If-Modified-Since请求头使用
4. 4开头的代表客户端错误
	- 400 Bad Request：请求语法错误或参数无效（如缺少必填字段）
	- 403 Forbidden：服务器拒绝执行请求（如用户无权限访问资源）
	- 404 Not Found：请求的资源不存在（如 URL 路径错误）
5. 5开头的代表服务器错误
	   1. 500 Internal Server Error：服务器内部错误（如代码异常导致崩溃）。
	   2. 502 Bad Gateway：作为网关或代理的服务器从上游服务器收到无效响应。
	   3. 503 Service Unavailable：服务器暂时不可用（如维护或过载）
### 7. get与post的区别
1. GET一般用来请求资源，适合查询操作，POST用来提交数据，适合修改操作；
2. GET参数通过URL查询字符串传递，仅支持URL格式的编码，参数暴露在地址栏中，长度受到浏览器限制，可以被浏览器缓存。
3. POST参数通过请求体传递，支持多种格式如表单格式，Json格式，对用户不可见，安全性比GET高，理论上没有大小限制，不可被缓存，每次都需要提交表单。

###  11. OKHTTP 连接池复用与 HTTP/2 多路复用的区别
1. 连接池是基于传输层，复用的是 TCP 连接，适用HTTP/1.1 和 HTTP/2，新的请求发起时，先检查连接池中是否有指向相同主机的，可用空闲连接，如果有直接复用。连接池大小默 为 5个，空闲时长最长为 5分钟；
2. 同一个连接上，多个请求也是串行执行，也就是所谓的“队头阻塞”。
3. 多路复用是基于应用层，只适用于 HTTP2，用于解决“队头阻塞”，实现真正的并行请求。
4. HTTP/2 在一个 TCP 连接上引入了“流”的概念，每个请求和响应被分配一个唯一的流 ID，请求和响应消息被分解成更小的二进制帧，按照 ID 进行区分，多个请求的帧会被打散交错的在连接上传输，一个请求的延迟不会阻塞其他请求的发送和接收。
### 12. OKHTTP 为什么高效
1. 连接池管理：复用 TCP连接，自动清理超时空闲连接；
2. 支持 HTTP2 多路复用
3. 自动重试与重定向
4. 责任链模式下轻松插入自定义逻辑如日志，认证和监控等；
5. 自动 GZIP，自动解压包含 Gzip 的响应头的响应数据;

# 架构设计
## 1. SOLID+ 迪米特法则
1. 单一职责：一个类只负责一项职责；
2. 开闭原则：针对修改关闭，扩展开放，通过继承和实现接口或组合扩展功能；
3. 里氏替换：子类必须能替换父类，保证继承关系中的一致性；
4. 接口隔离：接口功能要单一，客户端不应被迫使用不需要的接口；
5. 依赖倒置：高层模块不应依赖低层模块，两者都应依赖抽象；
6. 迪米特法则：一个对象只与直接相关的对象交互，应该对其他对象保持最少的了解；部长-主管-员工
## 2. MVx
1. 一个app的架构可以分为UI层，数据层和领域层，其中UI和数据层是必须的，领域层为可选的
	1. UI层也就是View层，负责在屏幕上展示应用的数据；
	2. 数据层也就是Model层，包含应用的业务逻辑并提供应用的数据；
	3. 领域层一般用来简化和重复使用页面层与数据层之间的交互；
2. MVC、MVP和MVVM主要的区别是领域层的实现方式不同；
3. 在MVC中，称为Controller层，通常由Activity和Fragment承担。由于xml的UI层功能较弱，Activity和Fragment还会承担大部分的UI层功能，导致代码臃肿，逻辑复杂；
4. 在MVP中，这一层称为Presenter层，为了隔离UI操作与业务逻辑，将View接口化，Presenter通过持有View接口来更新UI；MVP模式的缺点：
	1. 模板代码过多，每个页面都需要单独的View接口，
	2. Presenter层与View层强耦合，UI交互的修改，需要同步修改View和Presenter；
	3. Presenter层持有的View引用，需要手动管理View的生命周期；
5. 在MVVM中，这一层称为ViewModel，它不在持有View的引用，而提供数据流让View层订阅；
	- 核心实现依赖3个Jetpack组件，Lifecycle、Livedata和ViewModel，它们都能感知应用的生命周期，同时LiveData可以在数据变化时主动通知观察者，借助DataBinding还可以实现双向绑定；
6. MVVM 现在已经是主流的框架，介绍下它的工作模式的细节：
	1. MVVM遵循响应式编程范式，各模块之间的通信遵循特定的数据流向
	2. 数据从 View -> ViewModel -> Model->ViewModel->View，形成闭环
	3. ViewModel 与 Model 之间可以互相通信，而 View 通常持有 ViewModel 引用，并通过 LiveData或 StateFlow持有数据，来感知生命周期和响应 UI更新；
7.  MVI 中
	1. Model：表示 UI的状态，是唯一的数据源；
	2. View：接收一个 状态对象并渲染 UI，并将用户输入作为 Intent发送；
	3. Intent：表示用户的操作意图（如点击按钮、输入文本）
	4. ViewModel：接受 Intent，处理业务逻辑更新状态;
	5. MVI 强调的是“唯一可信数据源”与“单向数据流”
		1. 唯一可信数据源：
			- 唯一的意思不是说一个页面一个状态，而是将界面分成若干个相互独立的状态，控件状态不会相互影响；
			- 可信的意思是它是线程安全且不对外暴露修改方法，在 Android 中的实践就是采用 val 修饰，多线程写变量的时先拷贝源变量，然后对副本写。
		2. 单向数据流是指数据只能沿着一个方向流动，形成闭环。在 MVI 中就是，View 产生 Intent 触发 状态更新后 View 重新渲染；
	6. 和 MVVM相比， MVI严格限制单向数据流和唯一可信数据源，适用于状态复杂，交互频繁，对可预测性要求高的应用（~~可以很轻松的模拟状态来复现问题）~~；
## 3. 组件化
### 3.1  模块化与组件化
1. 模块化是按照功能或层级进行划分，主要关注的是代码层面的分离，但业务逻辑可能仍然是耦合的。比如`业务模块`直接依赖`用户模块`来获取用户信息。模块化的目的是让代码结构更清晰。
2. 组件化是在模块化基础上，更进一步解决业务耦合。每一个业务组件都可以独立开发和测试；
	- 组件之间通过路由框架进行页面跳转，通过组件暴露服务接口进行数据传递和服务调用；
### 3.2 组件化
1. 组件化采用分层架构的思想，上层组件只能依赖下层组件，一般至少可以划分为4层组件，从下到上依次为基础层，业务公共层，业务实现层，App宿主层
	1. 基础层：提供核心的与上层业务无关的基础能力，可以被上层组件直接依赖使用，如网络库、图片库、工具库等；
	2. 业务公共层：主要包含页面路由、公共UI组件、跨组件通信和服务接口。可被上层组件直接依赖使用；
	3. 业务实现层：业务核心实现层，包含原生页面、跨平台容器、业务服务实现。组件间不能直接依赖，只能通过调用页面路由或跨组件通信服务进行使用；
	4. App宿主层：主要包含APP主工程，启动流程、页面路由注册、服务注册、SDK参数初始化等组件，用于构建打包生成对应的App；
2. 组件化的作用
	1. 降低理解复杂度，做到更好的解耦和代码复用。每个组件做到职责单一，使用时带入最小的依赖，不仅是基础组件，业务组件也可支持复用。
	2. 隔离技术栈，独立开发和维护。不同组件可以使用不同的技术栈，对外暴露公共的API；

## 6. Livedata/ViewModel/Lifecycle
### 6.1 Lifecycle
1. 基于观察者模式实现，ComponentActivity会实现LifecyclOwner接口，创建LifecycleRegistry对象，它的作用是保存所有的Lifecycle的观察者；
2. 并向当前Activity注入一个空白Fragment或者AndroidR之后直接注册Activity的生命周期监听回调监听Activity的生命周期变化，当生命周期发生变化时，遍历观察者列表，通知观察者；
### 6.2 Livedata
1. 基于观察者模式实现，将所有的观察者保存集合中；
2. 对于指定了LifecycOwner的观察者 也就是Activity，还会将当前的观察者与Activity的生命周期绑定；只在Resume时接受数据变化，同时Activity销毁时，自动移除观察者；
3. 对于未指定LifecycOwner的观察者，需要手动移除，不然会有内存泄露的风险；
4. Livedata的粘性数据
	1. 2个页面同时使用一个Livedata，启动另一个页面，会接受到Livedata最后一次发送的数据；
	2. 粘性数据产生的原因是因为有2个条件可以触发通知观察者
		1. Livedata主动setValue：观察者保存在Livedata的观察者列表中
		2. Activity启动生命周期变化为Resumed状态；
		3.  而数据在下发过程中，首先检查Activity的状态，在检查观察者数据的版本号与LiveData的版本号，
		4. 粘性数据的解决方案，就是通过反射hook Livedata的observe方法，在注册新的观察者时就将观察者的版本号改成和最新Livedata一致；
5. set 与 post 的区别
	1. set 只能在主线程中调用
	2. post 允许在子线程中调用，通过主线程 handler post 到主线程中进行执行；
	3. post 存在值覆盖问题，post 值是首先将值保存在临时变量中，多次post，保留最新值，消息执行时取出临时变量的值；
### 6.3 ViewModel
1. Activity会实现ViewModelStoreOwner接口，创建ViewModelStore对象，通过map来保存所有的ViewModel
2. 当Configuration变化如横竖屏切换时，通过onRetainNonConfigurationInstance ，保存ViewModeStore;
3. Activity重建时，通过getLastNonConfigurationInsance 恢复ViewModelStore;
## 7. 高内聚和低耦合
1. 高内聚： 一个模块只负责一个明确、单一的功能，并且模块内的所有代码只为了完成这个功能；
2. 低耦合：模块与模块之间的相互依赖程度要尽可能的低。一个模块的变化，应该尽可能少地影响其他模块。
3. 这里的模块可以是一个类，一个函数或者一个组件；
4. 参考 6 大设计原则；

## 1. ANR
1. ANR的类型：
	1. 输入事件超时：应用在5秒内无法处理触摸、按键等输入事件；
	2. 广播接收超时：前台广播10s，后台广播60s未完成onReceive方法；
	3. 服务启动超时：前台Service在20s内、后台Service在200s内未启动完成；
	4. ContentProvider超时：10s内没有完成发布流程；
2. 产生原因
	1. 其中Service//BroadcastReceiver/ContentProvider的ANR机制类似，AMS在启动服务和广播时，会使用Handler发布一个定时message，如能正常完成，则移除此消息,否则触发ANR，ContentProvider特殊一点，它是跟随应用的Application启动而发布，AMS在attachApplication时 发送这个延时消息；
	2. 输入事件超时ANR有2种类型，分别为窗口未就绪和窗口处理超时。
		1. 输入事件由InputFlinger的InputDispathcer线程分发；
		2. 对 InputDispatcher 来说，每一个窗口都以一个 Connection 对象来维护，事件分发时，InputDispatcher 会先寻找到正确窗口的Connection 对象；
		3. 通过 Socket 通信将事件分发给应用窗口，如果分发失败此时ANR类型为窗口未就绪；
		4. 分发成功将事件加入到等待队列，下一次事件分发时，判断 等待队列中是否有事件在5s内没被移除，如果有就会认为发生了窗口处理超时；
3. ANR分析流程
	1. anr相关的日志有3种，mainLog也就是应用日志、 event日志和anr trace日志，首先对比3份日志，找到anr的起点时间，anr原因，anr进程，确定日志的有效性；
	2. 通过trace日志，检查主线程的状态
		1. main线程处于BLOCK、WAITING、TIMEWATING状态，那基本上是函数阻塞导致的ANR；
			1. BLOCK为阻塞等锁状态
			2. WAITING为等待唤醒如调用了wait方法
			3. TIMEWATING为指定时间的休眠如sleep
		2. main线程处于NATIVE状态,同时Looper.pollInner是表示当前Looper正常，没有阻塞，正在等待消息执行；
		3. 如果main线程无异常，则通过mainlog排查CPU负载和内存环境
	3. mainlog中会输出CPU负载和各个CPU的使用情况
		1. CPU负载是所有核心的累加结果，每个核满载为1
		2. 单个应用进程如果超过80%，就需要考虑应用本身的逻辑问题；
		3. iowait指标超过5%,或者日志中显示有大量的应用同时发生anr，可以认为是系统引起的ANR；
	4. event日志：
		- binder_sample：出现Binder通信阻塞时，可以通过这个tag过滤binder的使用情况。
		- wms和应用的生命周期情况结合 mainlog 中 changingfocus 与当前的 focusedWindow 确认当前窗口的状况；

### 2.2 内存问题分类

### 2.3 Java堆的内存泄露
1. 内存泄露的根本原因就是对象的存活时间超出了预期的生命周期；
2. 常见的场景：
	1. 静态实例持有外部对象致使外部对象无法回收；
		- 比如单例中错误持有Activity类型的Context
	2. 非静态内部类持有外部类对象，内部类对象的生命周期超过外部类
		-  比如在Activity中使用非静态的Handler
			1. 静态内部类+弱引用形式
			2. 在onDestory中通过handler.removeCallbackAndMessages(null)移除回调；
3. 异步线程/callback持有外部对象；（和非静态内部类类似）
4. 集合中元素持有外部对象的引用；
5. 资源对象未关闭；
### 2.4 Leakcanary的实现原理
1. Leakcanary是内存泄露检测框架，默认实现了对Activity/Fragment/Searvice/View 这四种对象的监控；
2. 它工作流程可以分为2部分，检测泄露对象和引用链分析
3. 检测泄露对象分为2步：
	1. 监控对象创建与销毁：
		1. Activity/Fragment：系统提供接口监听；
		2. Service：系统没有提供统一的生命周期监听方法，只能通过hook ActivityThread中的主线程的Handler消息和hook AMS 的serviceDoneExecuting方法确认要销毁的服务。~~message~~ c~~ode为116的消息（todo 哪里发的？）， 判断哪些服务准备销毁，~~
		3. View：这个View指DecorView，应用中的所有的DecorView都是保存在全局WindowManagerGlobal集合中，通过监听集合的添加和删除来实现对View的生命周期的监控。自定义集合实现对添加删除的监听反射替换WindowManagerGlobal中的集合；
	2. 当对象被销毁时，创建关联的弱引用并加入到全局引用队列中，5s后检查这个队列，如果这个对象被成功回收，队列就出会出现该对象，否则泄露；
4. 引用链分析：内存泄露发生后，dump当前的hprof文件，通过解析该文件获取最短引用链
	1. `hprof` 文件由文件头和 record 数组构成，每个 record 都有对应的 tag，收集 tag 为`gcroot`类型的 record.
	2. 遍历 `gcroot`队列，生成一颗以objectid为索引的字典树。根节点objecid 为 0，叶子节点为泄露对象，子节点为gcroot对象中的属性或元素，gcroot的子结点共有三种类型；
		1. 对于实例对象，子节点就是当前实例及父类中的所有非静态属性对应的对象；
		2. Class 对象，子节点为静态属性；
		3. 对象数组或集合，子节点为非空元素对应的对象；
	3.  在生成树的过程中，去掉重复和交叉路径，只保留泄露对象的最短路径，通过深度优先搜索获取所有泄露对象的路径集合
	4. 遍历集合生成通知信息
### 2.5 Native内存中Bitmap
1. 应用的OOM问题，大部分是Bitmap使用不当引起的，Android8.0之前，Bitmap占用的内存在Java堆中分配，8.0之后转为在Native堆分配；
	1. 对于8.0 之前的设备，采用 NativeBitmap 方案
	2. 对于 8.0 之后的设备，通过对 Bitmap 的构造方法进行字节码插桩，hookBitmap 的创建过程，在这个过程中监控 Bitmap 的大小，并按需对 Bitmap 进行缩放。
	3. 2 种方式的成本都比较大，应用更多还是要关注 Bitmap 的合理使用；
		1. 图片处理：按照需要大小加载图片，根据内存大小配置不同的色彩模式；
		2. 内存缓存：使用 LruCache 控制内存使用，监听 onTrimMemory 和应用的生命周期及时回收不再使用的 Bitmap;
		3. 对于明确是图片使用导致的OOM场景，try-catch Bitmap 的创建过程，捕获 OOM异常，按需对 Bitmap 进行缩放，主动释放内存；
2. 对于 BItmap 的内存泄露，解决方法和 Java 对象一样，Bitmap 的内存虽然在 Native 中分配，但是 Java也持有其句柄，Java层的对象释放后，Native 层通过 NativeAllocationRegistry 释放，通过分析 Hprof 文件中的 Bitmap 数量就可以确定是否泄露；

## 4. 一帧数据的绘制
1. 应用接受到app类型的VSYNC信号，唤醒等待中的UI线程，`Choroegrapher`回调`onVsync`开始一帧的绘制，依次处理Input事件，animation动画，performTraversals，其中traversal包含View的测量， 布局和绘制；
2. 绘制完成后，更新绘制数据，结束一帧的绘制，继续处理下一帧的Message，同时通过postAndWait唤醒渲染线程执行界面渲染任务。
3. 渲染线程先同步UI线程构建好的绘制命令树，然后通过dequeueBuffer申请一张处于free状态的buffer，进行GPU渲染，渲染完成后swipBuffer触发queueBuffer动作上帧；
4. 渲染线程通过queueBuffer唤醒对端的SurfaceFlinger进程中的Binder工作线程，申请sf类型的vsync信号；
5. sf类型的VSYNC信号到达后后，sf开始执行一帧的合成任务，之后再执行present唤醒HWC service进程执行图层合成送显；

## Linux的IO多路复用epoll原理
1. IO多路复是指允许单进程或单线程同时监听多个 fd的一种机制；
2. select 通过fd_set记录需要监听的文件描述符（运行时将其拷贝到内核空间，阻塞等待数据，内核检测到对应的fd 有数据 将fd_set置位后返回，用户再次遍历 fd_set，处理对应 fd 的数据；
	1. fd_set 是 bitmap，记录监听的文件在数组中的索引），
3. poll 的通过 pollfd 数组记录需要监听的 fd，解决 select 的数量限制；
4. epoll 有 3 个核心 API
	1. epoll_create：在内核创建一个 epoll 实例，包含红黑树和就绪队列链表；
		1. 红黑树存放所有添加进来需要监听的 fd
		2. 就绪链表存放所有已经就绪的fd;
	2. epoll_ctl：对红黑树节点进行操作,并指定fd要监听的事件类型；
		1. 添加时创建一个包含 fd 的 epollitem对象加入到红黑树中
		2. 同时设置 ep_poll_callback，当 callback 触发时，将对应的 fd 加入到就绪队列中；
	3. epoll_wait：阻塞等待数据，当有数据到达时，唤醒等待进程，将有数据到达的 fd加入到就绪队列中并拷贝到用户空间的 epoll_event 数组中；
## 什么情况下触发GC
- **堆内存利用率**：当堆内存使用达到约 80-90% 时可能触发 GC
- **分配失败**：当应用尝试分配对象但堆空间不足时立即触发 GC
## GC抑制
### GC触发的原因
1. Alloc GC：分配对象时，堆内存不足；
2. Background GC：对象分配成功后，内存使用率超过阈值触发，由 HeapTaskDaemon 线程完成；
3. 应用请求求分配大量Native内存时，但内存不足时触发 gc 回收被 Java 对象引用的 Native 对象；
4. 调用System.gc()显式执行；
### 实现步骤
1. gc 抑制主要是针对 BackGround GC;
2. gc 由HeapTaskDaemon 线程完成，它是一个守护线程，跟随 应用进程启动时运行，开始执行时会通过GetTask 获取HeapTask 集合中获取任务执行；
3. gc 抑制的思路有 2 种
	1. 添加一个自己的 HeapTask 到 tasks 集合中，阻塞 gc 线程；
	2. 修改系统 Task 的行为，让 task进入休眠阻塞 gc线程；
4. HeapTask有多种类型，最常见的是
	1. ConcurrentGCTask：当 Java 内存达到阈值时，执行此 task
	2. ClearedReferenceTask：当对象回收时执行，会讲当前回收对象加入的引用队列中；
5. 通过readelf查询符到ConcurrentGCTask的Run方法符号，利用inlinehook修改它的实现，增加延迟；
## PLT Hook 与 Inline Hook
1. PLT 修改GOT 表，适用动态链接函数，修改 GOT 表中的函数地址指针，使其指向自定义的 hook 函数;通常会保留原地址来选择性的调用原函数；
2. Inline Hook 直接修改函数开头的机器指令，插入跳转指令到hook函数，需要保存和恢复被覆盖的原始指令
